# 대량 일괄 변환 처리량 검증

2026년 10월 4일에 기준 커밋 `8d0a246`과 이 워크트리의 `batch.py`를 비교했다. 기본 작업자 4개에서는 첫 측정 10.3%, 반복 측정 10.8%의 처리량 증가를 관찰했다. 4,600개 Markdown 표본의 출력 SHA-256과 성공·실패·경고 결과는 모든 작업자 수에서 일치했다. 형식별 요소 지원을 추가한 작업은 아니므로 README의 Supported Elements 표를 바꾸지 않는다.

## 환경과 표본

사용자가 제공한 장비 정보는 Apple M5 Pro, 통합 메모리 48GB이다. 실행 환경에서 확인한 값은 macOS 26.6.2 arm64, Python 3.9.6, `os.cpu_count() == 15`이다. 외부 변환 엔진과 새 의존성을 사용하지 않았다. macOS 파일 캐시를 강제로 비우지 않았고 다른 워크트리의 작업과 열적 상태를 통제하지 않았다. 각 N은 첫 전후 측정을 한 번 수행했고, 4개와 15개는 전후 한 번씩 더 측정했다. 통계적 유의성이나 다른 장비의 개선율을 주장하지 않는다.

표본은 공개 코퍼스 파일 경로를 정렬한 뒤 고정 시드 `20261004`로 중복 없이 추출했다. HWP 2,000개, HWPX 1,000개, PDF 500개, DOCX 500개, PPTX 200개, XLSX 200개, XLS 200개로 총 4,600개이다. HWP/HWPX는 `corpus/hwp-public`과 `corpus/press-pairs`, PDF는 정책브리핑과 pdf.js의 공개 입력, Office는 Apache POI와 LibreOffice의 공개 테스트 입력을 사용했다. POI에 있는 DOCX 130개와 PPTX 95개만으로는 요청한 규모를 채울 수 없어 LibreOffice의 테스트 입력을 함께 사용했다. 다른 프로젝트의 구현 소스나 내부 문서는 읽지 않았다.

원본은 수정하거나 코퍼스에 복사하지 않았다. 임시 입력 목록은 심볼릭 링크로 만들었다. **배치의 링크 거부 정책을 유지하기 위해 측정 전용 수집 어댑터가 공개 원본 디렉터리에서 기존 `_collect_sources`를 실행하고 선정된 일반 파일만 반환했다.** 공통 코퍼스 루트의 identity와 상대 경로로 재표현했으며 작업자의 descriptor 검사, 크기 상한, 입력 snapshot, 출력 경로 검사와 원자적 쓰기는 그대로 실행했다. 수집 시간에는 선정되지 않은 공개 파일의 탐색 비용도 포함된다. 따라서 이 값은 선정 표본을 변환하는 `batch_convert` 경로의 측정이며, 링크 디렉터리 자체를 CLI에 전달한 측정값은 아니다. 링크 폴더를 직접 전달하면 기존과 같이 변환 대상이 0개이다.

출력은 작업자가 실제 쓰기·fsync·원자적 게시를 마친 뒤 1MiB 블록으로 해시하고 바로 삭제했다. Markdown 전체 출력의 누적 크기는 70,454,662바이트였으며 가장 큰 단일 출력은 14,712,830바이트였다. 측정 시간은 계측·해시·삭제 비용을 포함하며 프로파일 실행은 처리량 표에서 제외했다. 4,600개 실행의 해시·삭제 시간 합은 작업자 수별 전후 모두 0.40~1.23초였다. 일반 API 호출에 이 계측은 들어가지 않는다. 기준 소스 스냅숏은 하나만 사용했고 `.codex-work`는 전체 테스트 임시 파일을 포함해 확인 시 59MiB 이하였으며 검증 후 pytest 임시 파일과 스냅숏을 삭제했다.

## 병목 근거와 구현

기준 구현은 파일 하나당 `submit` 한 번을 실행해 모든 Future를 먼저 생성한다. 한 배치 안에서는 풀을 재사용하지만 배치 호출 사이에는 재사용하지 않는다. 작업자가 파싱과 출력 쓰기를 담당하고 작은 `BatchResult`만 부모로 보내므로 문서 전체나 큰 JSON 문자열이 IPC를 통과하는 병목은 처음부터 없었다. 230개 직렬 프로브에서 계측 필드를 붙이기 전 결과의 pickle 크기 합은 95,322바이트였다.

같은 230개 표본에 INFO 진행 로그를 켠 별도 cProfile 실행은 총 9.227초였다. 파싱 `_parse_dispatch`는 누적 8.111초, Markdown 렌더링은 0.296초, 기존 원본 수집은 0.424초, 출력 계획은 0.014초였다. snapshot 컨텍스트는 0.120초이고 그중 원본 복사는 0.019초였다. 원자적 출력 쓰기는 0.154초이며 그중 fsync는 0.012초였다. 진행 로그의 INFO 229회와 ERROR 3회는 합계 약 0.0066초였다. 이 누적 시간은 서로 포함되므로 더해서 전체 시간으로 해석하지 않는다. 출력 쓰기·로그·IPC를 제거할 근거는 없었다.

첫 작업이 시작되기까지 수집·출력 계획을 포함한 시간은 기준 병렬 실행에서 0.96~1.29초, 변경 후에는 0.85~1.02초였다. Python spawn과 모듈 로딩만의 비용을 따로 분리하지 못했다. 초기 작업자 로딩이 완료된 뒤 반복되는 reader import는 캐시 조회라 작았지만 초기 로딩이 무료라는 뜻은 아니다.

기준 8개 실행에서는 대부분의 작업자가 마지막 작업자를 2.5~2.8초 기다렸고, 변경 후에는 0.5초 이하로 줄었다. 12개·15개 실행에서도 기준 최대 꼬리는 각각 약 3.06초·2.84초였고 변경 후 약 0.53초·0.52초였다. 실제 느린 표본에는 `hwplib-big_file.hwp`, `press-pairs/156783912.pdf`, POI의 `ex45698-22488.xls`가 포함됐다. 원본 파일 크기와 변환 비용이 완전히 비례한다고 가정하지 않고, 이 표본에서 관찰한 꼬리 완화만 주장한다.

출력 이름은 기존 경로 순서대로 확정한 뒤, 이미 수집한 `source_size`가 큰 입력부터 배분했다. 동일 크기는 기존 순서를 유지한다. 그 다음 `wait(FIRST_COMPLETED)`로 완료 결과를 소비하고 비워진 제출 슬롯을 채운다. 대기 상한의 4는 작은 작업에서도 작업자가 굶지 않도록 둔 큐 여유값이며 최적 상수로 입증한 값은 아니다. 파일별 오류 격리·메시지·상태 필드는 기존 코드를 그대로 따른다.

chunksize를 늘려 여러 파일을 한 작업에 고정 배정하는 변경은 넣지 않았다. 실행 시간이 크게 다른 입력이 같은 묶음에 붙는 위험이 있고, 이번에는 원래 파일별 계약과 예외 처리를 유지하면서 확인된 꼬리부터 줄였다. 기본 작업자 수 변경, 배치 호출 간 전역 풀, fsync 제거, snapshot 복사 제거, parser 변경도 넣지 않았다. 전역 풀은 수명·동시 호출·옵션 격리 계약에 영향을 주기 때문이다.

## 출력과 실패 검증

Markdown은 모든 4,600개 표본을 작업자 1·4·8·12·15개에서 전후 비교했고, 반복 4·15개도 일치했다. 매번 성공 4,553개·실패 47개였다. 추가 JSON·텍스트 검증은 고정 시드의 별도 혼합 230개 표본에서 각각 작업자 1·4개로 실행했고, 매번 성공 227개·실패 3개, 전후 해시와 결과 필드 230/230개 일치였다. JSON·텍스트 전체 4,600개를 실물로 비교한 것은 아니다.

비교에는 성공 여부, 출력 상대 경로, error_count, 모든 경고·오류 문자열, 출력 바이트 수와 SHA-256을 넣었다. 코퍼스·출력 절대 루트와 snapshot의 난수 임시 경로만 정규화했다. 기존 병렬 결과도 완료 순서라 실행마다 순서가 달라지므로 배열 순서는 비교 대상에서 제외했다. 출력 바이트는 정규화하지 않았다. 실패의 원인을 새롭게 정상화하거나 숨기지 않았다.

TDD의 최초 실행에서는 제출 상한, 큰 입력 우선, 빈 입력의 풀 생성 방지 테스트 3개가 실패했고 기존 출력 일치 테스트 3개는 통과했다. 구현 뒤 새 테스트 9개와 기존 배치 테스트를 통과했다. 실제 spawn 작업자로 합성 DOCX 12개와 손상 ZIP을 세 출력 형식에서 비교했다. 합성 Future의 TimeoutError도 파일별 실패로 기록되고 다른 23개 변환이 계속 완료됨을 확인했다. 배치 API에 원래 실행 시간 제한 옵션이 없으므로 멈춘 작업자를 강제로 종료하는 타임아웃 기능을 새로 추가하거나 실물로 검증하지 않았다.

전체 검증은 `/usr/bin/python3 -m pytest tests/ -q -p no:cacheprovider --basetemp=.codex-work/pytest-tmp`로 실행해 **5,459개 통과·36개 건너뜀·14개 예상 실패**, 실제 실패 0개였다. `ruff check dochan scripts tests`와 `git diff --check`도 통과했다. 기존 테스트의 단언은 수정하지 않았다. Git index 쓰기가 차단되어 새 파일을 stage하지 못했으므로 새 파일의 로컬 절대 경로 금지는 별도로 검색했다.

## 재현과 증거

`probe_speed_batch.py`는 코퍼스·임시 폴더를 인자로 받고 표본 링크를 자동으로 삭제한다. 기준 package는 원본 커밋에서 한 번만 추출해 재사용한다. 아래 `DOCHAN_PUBLIC_CORPUS`는 실행자가 공개 코퍼스 루트로 설정하는 변수이다.

```bash
mkdir -p .codex-work/baseline
git archive 8d0a246 dochan | tar -x -C .codex-work/baseline
/usr/bin/python3 -m scripts.probe_speed_batch \
  --corpus "$DOCHAN_PUBLIC_CORPUS" --temporary .codex-work/probe \
  --source .codex-work/baseline --output .codex-work/before.json
/usr/bin/python3 -m scripts.probe_speed_batch \
  --corpus "$DOCHAN_PUBLIC_CORPUS" --temporary .codex-work/probe \
  --manifest .codex-work/before.json --reference .codex-work/before.json \
```
