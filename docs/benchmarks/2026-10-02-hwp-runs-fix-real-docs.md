## 상한과 폴백의 근거

중첩 본문을 포함한 모델 문단·각주 합계의 공개 최대는 HWP 131,072개, HWPX 31,301개였다. HWPX의 문단·각주 예산은 150,000자리다. 빈 XML 문단도 한 자리, 각주는 정의와 참조 문단을 위해 두 자리, 나머지 개체 경계는 뒤 문단이 분리될 가능성을 위해 한 자리를 예약한다. 메모도 예약하며 표·도형·머리글·각주 안의 문단을 빠짐없이 포함한다. 실제 모델보다 보수적인 예약량의 공개 최대는 39,441로 상한은 약 3.80배다. 모델 개수 최대의 약 4.79배라는 수치와 구별한다. 명세의 숫자가 아니라 측정에 근거한 구현 정책이다. 리뷰의 전체 요소 수를 문단·각주 개수로 대입하지 않았다.

선택된 XML 분기와 변경 추적 처리를 거친 본문을 문서 순서대로 예약한다. 초과 지점 이후에는 새 문단과 각주 모델을 만들지 않고 표시 문자열을 모아 문서 전체에서 하나의 무서식 문단으로 확정한다. 뒤 섹션, 중첩 각주·표·도형 본문도 이 꼬리에 포함된다. 각주 정의의 내용도 본문에 합쳐지며 원래 각주 번호와 문단·개체 구조, 서식과 링크는 보존하지 않는다. 양식의 비밀번호 비출력 정책, 선택된 switch 분기, 글자 겹치기, 줄바꿈과 수식 원문은 기존 해석을 재사용한다. 예약 상한 외에는 폴백 문단 하나만 추가된다. 반복 문자열 덧붙이기 대신 StringIO를 사용한다. 각 예산의 WARN은 문서당 한 번이며 파서 재사용 때 초기화한다.

HWP의 문단은 PARA_HEADER 또는 양식 CTRL_HEADER, 각주는 각 CTRL_HEADER에 대응한다. 도형·캡션·셀의 문단도 레코드 트리를 방문하여 생성한다. PARA_TEXT 안의 각주 제어문자를 10,000번 반복한 합성 입력에서도 각주 모델은 생성되지 않았다. 따라서 TextRun의 글자모양 쌍과 달리 문단·각주가 레코드 상한 밖에서 증폭하는 경로는 확인되지 않았다. 문서 레코드 상한 1,300,000개와 셀·바이트·깊이 상한을 유지하며 별도 HWP 문단 병합 제한은 추가하지 않았다. 640,000개 문단 입력은 1,280,000개 레코드로 상한 이내이므로 그대로 보존한다.

서식 예산에서 기본 서식 단일 런의 출력이 그대로면 경고하지 않는다. JSON 런 경계가 합쳐지거나 실제 서식·링크가 소실되면 경고한다. 기존 단일 run 안 필드 팬아웃 테스트의 경계 병합 경고 계약도 유지했다. 중첩 각주·도형을 해석하기 전에 앞 텍스트를 확정하며, 빈 개체를 만났을 때는 임시 예약을 되돌려 이전 JSON 경계를 보존한다. 거부된 HWP 표의 캡션에 사용한 런 예약도 반환한다.

이전 보고서의 131,072는 최대 문서의 모델 런 수이면서 문단 수다. 한 문단의 서식 분할이 131,072개였다는 뜻이 아니다. 문단당 원시 글자모양 쌍의 공개 최대는 152개다. 같은 위치의 빈 런 미생성은 기존 동작이며 최초 구현의 변화는 쌍 튜플 목록 제거와 예산 미소비다.

## 공격 입력의 공개 API 측정

Apple M5 Pro·48GB·macOS의 Python 3.9에서 입력 조립을 끝낸 뒤 조건마다 새 프로세스를 실행했다. 아래는 최종 소스로 다시 측정한 조건별 1회 결과다. API 시간은 Dochan 생성과 Markdown·JSON 직렬화의 합이며 RSS는 프로세스 최고값이다. HWP는 OLE 스트림 경계 대역을 사용하므로 OLE 디렉터리 해독 비용은 포함하지 않는다. HWPX는 실제 ZIP 입력이다. 본문 문자는 모델·Markdown에서 N개, JSON의 문단·런 text에서 2N개인지 확인했으며 모든 조건에서 일치했다.

각주 조건은 빈 각주 600,000개와 그 뒤의 검증용 본문 문자 600,000개를 여섯 섹션에 담았다. 문단과 책갈피는 섹션당 100,000개 이하로 분리했다. 따라서 기존 XML 토큰 상한에 걸려 입력을 버린 결과가 아니다.

| 형식·입력 | 개수 | 압축 bytes | 문단+각주 전→후 | API 초 전→후 | 최고 RSS MiB 전→후 | WARN 전→후 |
|---|---:|---:|---:|---:|---:|---:|
| HWP 교대 서식 구간 | 3,000,000 | 4,915,789 | 1 → 1 | 4.559 → 4.575 | 1311.6 → 1308.2 | 1 → 1 |
| HWPX 교대 서식 구간 | 300,000 | 49,092 | 3 → 3 | 2.260 → 2.709 | 417.4 → 414.5 | 1 → 1 |
| HWP 기본 서식 문단 | 640,000 | 63,653 | 640,000 → 640,000 | 11.531 → 11.441 | 2520.9 → 2517.7 | 1 → 0 |
| HWPX 기본 서식 문단 | 1,000,000 | 131,000 | 1,000,000 → 150,001 | 23.021 → 8.691 | 4002.2 → 705.6 | 1 → 1 |
| HWPX 빈 각주와 뒤쪽 본문 | 600,000 | 60,462 | 1,200,006 → 149,999 | 22.927 → 4.243 | 3463.4 → 506.4 | 0 → 1 |
| HWPX 책갈피 경계 | 600,000 | 99,840 | 6 → 6 | 5.660 → 7.544 | 515.4 → 511.0 | 1 → 1 |

문단·각주 공격의 모델 및 직렬화 증폭은 줄었다. 기존 서식 구간·책갈피 입력에서는 문단 예약을 위한 순회 비용이 추가되므로 모든 입력이 빨라진다고 주장하지 않는다. 기존 HWP 대량 문단의 메모리 비용도 남는다. XML DOM·원시 문자 맵·본문 문자열 자체를 일정 크기로 만드는 변경은 아니다.

초기 수정에서 큰 XML 하위 트리를 그대로 분리하자 60만 각주 입력의 파싱이 약 33초로 느려졌다. 프로파일링에서 구조 예산 처리에 시간이 집중되는 것을 확인하고, 텍스트를 수집한 뒤 연결된 상태에서 하위 노드를 비워 제거하도록 수정했다. 위 표에는 이 문제까지 고친 최종 결과를 사용했다.

## 재현 방법

`CORPUS`는 공개 코퍼스, `BEFORE`는 기준 커밋 `44c6733`의 별도 소스 경로다. 내부 문서는 쌍 비교 함수의 결과를 익명화하고 내용과 파일명을 저장하지 않았다.

```bash
/usr/bin/python3 -m scripts.probe_hwp_runs "$CORPUS" --source-root "$BEFORE" --output .codex-work/fix-before.json
/usr/bin/python3 -m scripts.probe_hwp_runs "$CORPUS" --compare .codex-work/fix-before.json --output .codex-work/fix-final.json
/usr/bin/python3 -m scripts.benchmark_hwp_runs --source-root "$BEFORE" --format hwpx --pattern paragraphs --count 1000000
/usr/bin/python3 -m scripts.benchmark_hwp_runs --source-root . --format hwpx --pattern paragraphs --count 1000000
/usr/bin/python3 -m scripts.benchmark_hwp_runs --source-root . --format hwpx --pattern notes --count 600000
/usr/bin/python3 -m scripts.benchmark_hwp_runs --source-root . --format hwpx --pattern bookmarks --count 600000
/usr/bin/python3 -m scripts.benchmark_hwp_runs --source-root . --format hwp --pattern paragraphs --count 640000
/usr/bin/python3 -m scripts.benchmark_hwp_runs --source-root . --format hwp --pattern runs --count 3000000
/usr/bin/python3 -m pytest tests/ -q -p no:cacheprovider --basetemp=.codex-work/pytest-tmp
```
