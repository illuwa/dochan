# HWPX 전문화 — 마이크로 태스크 병렬 실행 계획

상태: 일부 범위 구현·검증, 나머지는 계획. 최초 설계 기준 커밋: `db2ab35`.
대상: HWPX 의미 보존·진단·성능. Office/PDF 신규 기능은 범위 밖.
2026-09-19 현재 상태는 [구현·검증 기록](../../benchmarks/hwpx/implementation-progress.md),
의존성·소유권 정정은 [범위 검토](hwpx-subagent-feasibility.md)를 기준으로 한다.
아래 66개 행은 작업 분해와 완료 조건이며 전체 완료 목록이 아니다.

## 1. 확인된 기준선과 주의점

- 현재 테스트 결과와 재현 명령은 [구현·검증 기록](../../benchmarks/hwpx/implementation-progress.md)에 기록한다. 초기 설계 때의 테스트 수를 현재 결과로 사용하지 않는다.
- 실물 검증은 공개 표본의 고정 SHA-256과 독립 XML gold 범위로 구분한다. 비공개 문서 묶음의 탐색 측정을 공개 정확도·성능 근거로 사용하지 않는다. 정식 성능/RSS 비교는 남아 있다.
- parser.py가 패키지·서식·본문·표·이미지 처리를 대부분 소유한다. 무작정 기능별로 이 파일을 동시에 수정하면 충돌한다.
- conversion.Provenance, ConversionOptions.include_assets, 모델 provenance 필드가 이미 있다. 새 유사 모델을 만들기 전에 재사용한다.
- 이미지 데이터 캐시와 ZIP 이름 set도 이미 있다. 중복 구현 금지.
- charPr 실제 ID 조회와 표 셀 재파싱 방지는 현재 구현되어 있다. `tests/test_hwpx_regressions.py`로 ID·각주·중첩 표 예산을 검증한다. 서식 우선순위 전체나 속도 향상의 증거는 아니다.
- 변경 추적·차트는 공개 XML 조사와 일부 제품 구현까지 연결되었다. 실물 gold의 범위 밖 의미와 스타일 상속은 별도 규격 확인이 필요하다. 특히 next style은 부모 스타일이 아니다.
- graphify 그래프의 줄 번호가 현 소스와 다르므로 길잡이로만 사용한다.

## 2. 작업 규칙

### 역할과 파일 소유권

| 담당 | 독점 소유 경로 | 역할 |
|---|---|---|
| I 통합 | dochan/hwpx/parser.py, reader.py, cli.py, batch.py | 기존 진입점 연결, API 호환성 |
| M 모델/출력 | dochan/model/*, conversion.py, output/* | 공용 계약 및 직렬화; 다른 포맷 회귀 보호 |
| Q 데이터/검증 | scripts/hwpx_*, tests/fixtures/hwpx_audit/*, docs/benchmarks/hwpx/* | 코퍼스·정답·측정 |
| S 서식 | dochan/hwpx/styles.py, numbering.py, tests/test_hwpx_styles.py, test_hwpx_numbering.py | 서식/목록 독립 해석 |
| R 변경 추적 | dochan/hwpx/revisions.py, tests/test_hwpx_revisions.py | 변경 이벤트/보기 투영 |
| C 차트 | dochan/hwpx/charts.py, tests/test_hwpx_charts.py | 차트 제목·계열·값 |
| D 진단/위치 | dochan/hwpx/diagnostics.py, provenance.py, tests/test_hwpx_diagnostics.py, test_hwpx_provenance.py | 위치·미지원 보고 |
| P 성능 | dochan/hwpx/package.py, streaming.py, tests/test_hwpx_package.py, test_hwpx_streaming.py | 패키지/스트리밍 후보 |

신규 경로는 계획상의 경로다. 소규모 변경만 필요하면 모듈 생성 없이 I가 통합한다. 구조 분리를 위한 대규모 전면 재작성은 하지 않는다.
공용 파일을 다른 담당자가 수정해야 하면 패치 요구사항과 재현 테스트만 I/M에 전달한다. 같은 wave에서 파일 소유권을 겹치지 않는다.
최대 동시 구현 4개 권장. 성능 측정은 다른 테스트·빌드·LLM 작업이 없는 슬롯에서 단독 실행한다.

### 태스크 단위 완료 조건(모든 ID 공통)

1. 선행 작업과 계약 버전 확인, 배정 경로 read 후 작업.
2. 새 기능/버그는 실패 테스트 작성 → 실제 실패 출력 확보 → 최소 구현 → 통과.
3. 단일 태스크 목표 30~90분의 집중 작업. 90분을 넘으면 새로운 하위 ID로 분할. 시간은 추정이며 완료 보장이 아니다.
4. 인계: 변경 경로, 실패/통과 명령과 결과, 실물 검증 여부, 미지원 사항, 다음 의존성.
5. 상태는 pending/ready/running/review/verified/blocked. 코드만 존재하면 verified 불가.
6. 전체 테스트는 `python -m pytest tests/`로 실행한다. `python`은 의존성이 설치된 프로젝트 환경의 인터프리터다. 검증에 사용한 버전은 Python 3.9.6, pytest 8.4.2이며 환경이 바뀌면 먼저 확인한다.
7. 커밋·푸시는 사용자 요청 때만. 기능 브랜치/분리 작업공간에서 구현하고 main 직접 커밋 금지.
8. 실물 자료가 없으면 구현 테스트 통과와 실물 검증을 분리 표기하고 지원 ✅는 보류한다. 외부 업로드/비공개 문서 배포 금지.

초기 제안 인터페이스(아래는 현재 API 명세가 아니다. 현재 계약은 각 검증 문서 참조):
- StyleResolver.resolve(style_id, para_id, char_id) → 해석된 서식 + 진단.
- RevisionResolver가 XML을 임의 변형하지 않고 이벤트 범위를 해석; projection(final/original/all)은 별도 함수.
- ChartReader.read(part, bounded_package) → 구조화 차트 + 진단; 네트워크 접근 없음.
- DiagnosticCollector.add(code, location, detail), 상한 후 요약 카운트.
- 위치는 part URI와 네임스페이스 URI 기반 경로; 동일 문단이 출력에서 분할되면 원본 경로와 fragment 구분.
- 모든 순회 상태는 문서/파서 인스턴스 범위. 전역 mutable cache 금지.

성능 개선은 default 동등 출력끼리만 판정한다. include_assets=False는 별도 제품 옵션이며 기본 모드 대비 우위 주장에 섞지 않는다.
스트리밍은 필수 구현이 아니라 측정 기반 결정이다. 초기 일반 최적화 목표는 baseline 대비 20% 이상 개선 후보 발굴이며, 입증되지 않으면 결과를 그대로 보고한다.

## 9. 실행 순서와 병렬 배치

- 배치 0a(4개): A01(Q), A02(S), A03(R), A04(C).
- 배치 0b: A05(D), A06(P), A07→A08(Q), A09(S). 같은 담당의 화살표 작업은 직렬.
- 배치 1: K01→K02→K03→K04→K05→K06. 동시에 Q는 P01→P02→P03 및 V01을 직렬 수행 가능.
- 배치 2a(4개): S01→S04, R01→R06, C01→C05, D01→D06. D 내부 D04는 D03 뒤 실행해 파일 충돌 회피.
- 배치 2b: 준비된 I01/I03 통합 + S05→S07 + P04/P07/P08 + M 출력 큐. 통합자 파일 예약으로 최대 4개 유지.
- 배치 3: P05/P06 및 I02/I04/I05는 I 큐에서 직렬. P09는 단독 성능 슬롯, 채택 시 P10도 I 큐.
- 배치 4: O01→O04, I06. 완료된 I 작업의 O 작업은 앞당길 수 있다.
- 배치 5: V02→V03→V04→V05→V06→V07.

핵심 DAG:
조사 → 계약 → 독립 해석 모듈 → 파서 연결 → 출력/API → 홀드아웃 → 전체 스캔 → 성능 → 리뷰.
빠른 1차 마일스톤: A/K + S01~S04 + D + P01~P06 + I01/I03/O01.
2차: 목록·변경 추적·차트. 3차: 채택된 스트리밍 및 최종 공개 비교.
1차를 먼저 릴리스 후보로 끊는 경우 V 게이트의 의존성은 포함 작업만으로 명시적으로 갱신한다.
