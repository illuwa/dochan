# 검증 코퍼스와 정답지

dochan 은 합성 단위 테스트만으로 지원 여부를 판정하지 않는다. README `Supported Elements` 의 ✅ 는 단위 테스트와 **실물 문서 검증**을 모두 통과한 칸에만 붙는다.
검증에 쓰는 실물 문서는 프로젝트가 진행되면서 계속 늘었고, 새 코퍼스가 들어올 때마다 이전에 보이지 않던 결함이 드러났다. 이 문서는 지금까지 모은 코퍼스와 정답지의 종류, 그리고 그것을 쓰는 원칙을 정리한다.
칸별 상세 기록(표본 파일·정답 근거·기대·실제·판정)은 [`docs/benchmarks/`](benchmarks/)에, 형식별 한계는 [`docs/SUPPORT_NOTES.md`](SUPPORT_NOTES.md)에 있다.

## 늘어난 과정

1. **2026-06 — 내부 삼중 짝.** 같은 문서를 한컴오피스로 HWP·HWPX·PDF 로 저장한 짝으로, HWPX 리더를 정답 삼아 HWP 바이너리와 PDF 리더를 맞추는 방식이 여기서 시작됐다.
2. **2026-07-27 — 공개 HWP·HWPX 수천 개.** 처음 6,977개로 시작한 회귀 코퍼스는 지금 7,076개다. 모든 리더 변경은 이 전체를 전후 비교해 의도하지 않은 출력 변화가 0 인지 확인한다.
3. **2026-10-02 — Office·PDF 공개 실물.** Apache POI·LibreOffice·pdf.js·Tika 테스트 자료를 들여와 legacy Office(DOC·PPT·XLS)를 OOXML 짝으로 검증하고, PDF 를 983개 변종으로 전수 비교하기 시작했다. 이 자료로 README 의 ⬜ 칸이 71칸에서 9칸으로 줄었다(1.7.0, 2026-10-03).
4. **2026-10-03 — 원 프로그램을 정답으로.** 한컴오피스(Mac) 화면 캡처로 HWP 취소선·밑줄·콤보 상자 표시값을, Microsoft PowerPoint 실측으로 PPT·PPTX 글자 서식 상속 규칙을 확인했다. Excel 이 저장한 `TEXT()` 캐시는 셀 서식기의 정답으로 썼다.
5. **2026-10-04 — 공개 삼중 짝과 보류 묶음.** 내부 짝에만 있던 "같은 문서의 HWP·HWPX·PDF" 를 공개 보도자료로 확보해(375건) PDF 각주·줄 경계 공백·HWP 글자 겹침·HWPX 첨자 같은 결함을 공개 근거로 찾고 고쳤다. 같은 날 조정에 한 번도 쓰지 않은 217건을 보류 묶음으로 따로 받았다. PDF 줄 안 어절 공백 규칙은 이 묶음 206쌍에서 한 번 재어 새 공백 1,888개가 모두 HWPX 와 일치했고(`scripts/probe_pdf_word_gap.py`), 제목 감지 규칙은 규칙을 모르는 판독자가 26문서 372문단의 PDF 렌더를 보고 매긴 라벨(`docs/benchmarks/2026-10-04-heading-blind-labels.json`, 제목 50개)로 평가해 정밀도 21/25·재현율 21/50(이전 0/50)을 확인하고 채택했다. 같은 단서로 만든 대리 라벨(정밀도 90%)보다 낮게 나와, 대리 라벨이 낙관적이라는 점도 이 평가로 드러났다. 두 번째 보류 묶음(34문서 580문단, 제목 70개)에서는 정밀도 44/65(68%)·재현율 44/70(63%)이었고, 판독자 사이에서도 갈리는 "괄호 태그 진술 줄"이 주된 오검출로 드러났다(`docs/benchmarks/2026-10-04-heading-blind-labels-2.json`). 진술 줄을 제외하는 규칙은 세 번째 보류 묶음(574문단, 제목 95개)에서 제목 손실 없이 정밀도 77.5% → 83.1% 를 확인하고 넣었다(`docs/benchmarks/2026-10-04-heading-blind-labels-3.json`). 판독 라벨은 모두 1,526문단이다. PDF 각주 규칙도 세 보류 묶음의 HWPX·PDF 635쌍에서 한 번 쟀다: HWPX 각주가 있는 문서는 1개(각주 1개)뿐이었고 PDF 에서 그 1개를 복원했으며, 각주가 없는 634문서에서 가짜 각주는 0개였다(양성 표본이 적어 README 칸은 ⬜ 그대로).

## 정답지의 종류

- **같은 문서의 다른 형식.** HWPX 를 정답으로 HWP·PDF 를, OOXML(DOCX·PPTX·XLSX)을 정답으로 DOC·PPT·XLS 를 비교한다(`scripts/compare_hwp_pairs.py`, `scripts/compare_pdf_pairs.py`, `scripts/compare_office_pairs.py`).
- **원 프로그램의 실제 동작.** 한컴오피스 화면, Microsoft PowerPoint 가 보고하는 서식, Excel 이 저장한 계산 캐시. 화면을 쓰는 실측은 저장소 밖 절차로 하고 결과만 기록한다.
- **공개 테스트의 기대값.** POI·LibreOffice 테스트가 단언하는 문자열·개수. 기대값만 읽고 구현 코드는 보지 않는다([라이선스 원칙](../AGENTS.md#라이선스-원칙)).
- **제품 코드와 분리된 독립 해독기.** 검증 스크립트가 명세대로 원시 바이트·XML 을 직접 읽어 리더 출력과 대조한다(예: `scripts/probe_xls_textbox.py`, `scripts/probe_xlsx_shape_text.py`). 저장소 밖 venv 의 독립 라이브러리(xlrd 등)는 비교용으로만 쓴다.
- **렌더 판독 라벨.** PDF 를 PDFium·Poppler 로 렌더해 사람이나 감수 에이전트가 눈으로 판정한 라벨. 휴리스틱(제목 감지·각주·표)의 정밀도·재현율을 잰다. 휴리스틱과 같은 단서로 자동 생성한 대리 라벨은 낙관적일 수 있으므로 보류 문서의 판독 라벨로 다시 확인한다.

## 원칙

- **조정과 평가를 나눈다.** 규칙과 상수는 개발 묶음(예: `corpus/press-pairs` 의 짝수 newsId)에서 정하고, 보류 묶음(홀수 newsId, `corpus/press-pairs-holdout`)에서는 한 번만 잰다. 보류 결과를 보고 규칙을 고치면 그 묶음은 더 이상 보류가 아니라고 기록한다.
- **오류·경고 전수 점검.** 공개 실물 전체(2026-10-04 기준 13,494개)를 파일마다 따로 읽어 dochan 이 남긴 오류·경고를 유형별로 모으고, 정상 파일에서 나는 메시지를 결함 후보로 본다(`scripts/probe_error_sweep.py`). 첫 점검에서 정상 파일의 결함 5건을 고쳤고, 나머지 후보는 원본 손상 근거를 기록했다. 처리 중 예외·시간 초과는 0건이었다. 새 묶음이 들어오면 다시 돈다: 보류 묶음 2·3(1,007개)에서는 예외 0건, 메시지가 있는 파일 2개였고 그중 한컴 PDF 의 이스케이프 안 된 `)` 가 세 번째로 재현돼 복구 규칙을 넣었다.
- **같은 문서 짝 전수 일치 점검.** 공개 HWP·HWPX 같은 이름 짝(2026-10-04 기준 같은 문서로 확인된 573쌍)을 HWPX 를 정답으로 문서 단위 지표(Markdown 일치, 표 서명, 제목·수식·각주·그림 개수)로 전수 비교하고 차이를 원인별로 묶는다(`scripts/probe_hwp_parity_sweep.py`). 첫 점검에서 HWP 그림 설명 결함 2건을 고쳐 일치가 257→387쌍이 됐다.
- **전수 회귀는 해시로.** 코퍼스 전후 비교는 문서별 출력 SHA-256·글자 수·오류 목록만 저장하고, 차이가 난 문서만 들여다본다(디스크 사용 제한).
- **내부 문서는 집계만.** 내부 짝의 파일명·내용은 코드·테스트·문서·커밋 어디에도 남기지 않는다.
- **거짓 체크 금지.** 실물 표본이 없거나 정답지를 만들 수 없는 칸은 ⬜ 로 남기고 이유를 적는다(예: DOC 내장 차트 — 공개 DOC 490개에 차트가 든 문서 0개).
