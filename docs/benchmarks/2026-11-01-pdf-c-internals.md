# PDF C 내부 계측과 할당 비용 감소

기준 HEAD는 `56b0fcd5d448f4b7d68a811a9e48f4ae745f0cfc`다. 같은 HEAD의 읽기 전용 기준 체크아웃과 비교한다. 커밋·푸시는 하지 않는다.

## 변경

- `_cinterp`: 속성·사전 키·메서드 이름 9개를 재사용하고, 초기화 완료 여부를 한 번 검사한다. 단일 글리프의 검증된 exact Unicode는 연결 함수를 거치지 않는다.
- `_clines`: 이미 정렬된 행은 동일한 엄격 비교로 확인하여 병합 정렬의 임시 복사를 생략한다. 동률과 signed zero 순서는 그대로다. 조각당 하나인 세그먼트 목록은 정확한 길이로 할당한다.
- `_cobjects`: 동작 변경 없이 숫자·이름·배치·간접 객체·단일 객체 호출의 내부 계측을 추가한다.
- `DOCHAN_PROFILE_INTERNALS`에서만 monotonic `clock_gettime`과 호출 카운터가 들어간다. 일반 빌드에는 `_profile` API나 타이머 심볼이 없다. 계측 헤더를 sdist와 빌드 의존성에 연결한다.
- 새 의존성, 외부 엔진 코드, 부동소수 연산 순서 변경, 공개 데이터 모델 변경은 없다.

## 왕복과 미채택 범위

`BDC/BMC`는 properties 조회, MCID 중복 집합, 깊이 초과 경고와 연결된다. `EMC`도 교체 가능한 Python 메서드를 호출한다. `Do`는 Form 로더·순환/확장 예산, `gs`는 리소스 조회와 상태 전달을 수행한다. 이를 C에서 생략하려면 콜백 identity와 부작용 계약을 추가로 증명해야 하므로 이번 후보는 기존 yield를 보존한다. 순서를 결정하는 set/dict 사용을 새로 이식하지 않았다.

## 최종 소스의 첫 교대 측정

같은 공개 300개를 전·후·후·전·전·후 순서로 별도 프로세스에서 `Dochan(path)` 파싱한 합계다. 측정 중 이 작업의 테스트·퍼징·sanitizer는 실행하지 않았다.

| Python | 전 3회 (초) | 후 3회 (초) | 중앙값 전 → 후 (초) | 관측 변화 |
| --- | --- | --- | --- | --- |
| 3.9.6 | 8.709 / 7.774 / 7.410 | 7.721 / 7.701 / 7.938 | 7.774 → 7.721 | 0.69% 감소 |
| 3.12.12 | 6.233 / 9.294 / 8.884 | 5.992 / 6.570 / 8.042 | 8.884 → 6.570 | 26.04% 감소 |

**두 환경 모두 PDF 합계 10% 감소라는 목표는 입증하지 못했다.** 특히 3.12는 회차 변동이 커서 관측 중앙값의 감소를 안정된 개선율로 일반화할 수 없다. 전수 측정 시작 직후 시스템 load average는 11.68 / 11.40 / 7.48이었다. 샌드박스에서 프로세스 조회가 제한되어 장비 전체의 다른 부하가 없다는 조건을 확인하지 못했다. 이 결과만으로 합류를 승인하지 않는다.

## 재현과 원자료

- 일반 빌드: `DOCHAN_BUILD_ACCEL=1 python setup.py build_ext --inplace --force` (Xcode 3.9).
- 계측 빌드: 위 명령에 `CFLAGS='-O3 -DDOCHAN_PROFILE_INTERNALS -DDOCHAN_PROFILE_SHOW'`를 추가한다. 계측 후 반드시 일반 빌드로 복구한다.
- 계측 조회: 세 모듈의 `_profile()`은 8칸 `(누적 wall 초, 호출 수)` 목록을 돌려준다. `_cinterp` 슬롯 0–4는 next/scanner/show/fragment/operate, `_clines` 0–2는 assemble/read/row, `_cobjects` 1–5는 number/name/batch/indirect/parse다. 사용하지 않는 칸은 0이다. 누적 카운터이므로 측정마다 새 프로세스를 쓴다.
- 계측 테스트: `DOCHAN_EXPECT_INTERNAL_PROFILE=1 python -m pytest tests/test_pdf_cinternals.py -q -p no:cacheprovider`.
- 글자 차등: `python -m scripts.probe_pdf_show_full <공개 PDF 루트들> --cases 100000`.
- 객체 차등: `python -m scripts.probe_pdf_objects --paths <공개 PDF 목록 JSON> --count 100000`.
- 전체 테스트: `python -m pytest tests/ -q -p no:cacheprovider`; 같은 명령을 `DOCHAN_DISABLE_ACCEL=1`로 반복한다.
- 출력 비교는 기존 `scripts.probe_output_speed.collect`와 `compare_records`를 사용한다. roots를 공개 PDF 2,281건으로 제한한다.
- 작업 기록의 `bench.json`은 추가 교대 측정의 두 Python별 여섯 회차 합계와 loadavg, `bench-loaded.json`은 최종 소스 첫 교대 묶음, `profile-*-O3.json`은 계측 원자료, `hash-*.json`은 전수 결과, `regression-*.json`은 파일별 판정이다. `fuzz-*.log`, `sanitizer-*.log`, `sanitizer-source.json`, `tests-*.log`, `strict-final.log`, `ruff.log`가 검증 근거다. 실행 wrapper와 줄 차등 재현 코드는 작업 기록에 보존한다.

측정은 macOS 26.6.2 arm64에서 했다. Linux·Windows, 다른 CPU, 누수 탐지는 검증하지 않았다. 출력 해시와 차등 비교는 기존 구현과의 동일성을 증명하며 PDF 추출의 의미적 정확성을 새로 보증하지 않는다.

## 큰 회귀 항목의 원인 진단과 판정

전수 판정의 상위 8개 파일을 별도 입력 묶음으로 각각 20회 실행하고 GC 콜백의 시간·횟수를 기록했다. 이 진단은 전수 gate를 대체하지 않는다.
`156782183.pdf`는 전수 최솟값 67.906→228.043ms(3.36배)였지만, 별도 진단 중앙값은 80.221→80.942ms(1.009배), GC 중앙값은 8.499→8.736ms였다.
8개 모두 진단 중앙값의 비율이 0.993–1.017이었고 GC 횟수 중앙값도 전후 같았다. 따라서 큰 지연을 코드의 지속적 회귀로 재현하지는 못했다. 장비 부하와 문서 실행 순서에 따른 GC 시점 중 어느 쪽이 주원인인지는 확정하지 못했다.

**합류 보류**다. 출력 동일성·차등·sanitizer·전체 테스트는 통과했지만, 정해진 전수 성능 gate의 회귀 0건과 두 Python 모두 10% 개선을 만족하지 못했다. 무부하 조건 역시 증명하지 못했다.
코드와 계측·원자료는 검토 가능한 미커밋 후보로 남겼다. 커밋·푸시·합류는 하지 않았으며, 생성된 build와 계측/sanitizer 소스 복사본은 정리했다. 일반 가속 바이너리는 최종 소스 빌드 상태다.
