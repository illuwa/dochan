# HWP 속도 개선: 일괄 디코딩·트리 보정 (2026-11-02)

**작업자는 목표인 HWP 전체 파싱 합계 15% 감소를 입증하지 못해 미채택으로 보고했으나, 오케스트레이터가 한가한 장비에서 다시 재서 합류를 채택했다.**
교대 3회 중앙값으로 HWP 파싱 −11.0%(Python 3.12)·−11.9%(3.9), 출력 해시 14,491건 차이 0, 파일별 1.2배 회귀 0건이다([통합 재측정](2026-11-02-round4-integration.md)). 아래 작업자 측정은 동시 부하(약 37)에서 잰 참고값이라 wall 이 흔들렸다.

## 후보 구현과 범위

외부 구현을 열람하지 않고 다음 후보를 자체 작성했다. 새 의존성·C 모듈은 추가하지 않았다.

- 정렬된 일반 BMP UTF-16LE 구간을 일괄 디코딩하고 문자별 `unpack`·`chr`·리스트 조작을 줄였다.
  제어 블록·surrogate·홀수 끝 바이트·모든 WCHAR→텍스트 경계 해석은 유지했다.
- LIST_HEADER 최대 5회 보정에서는 정수 레벨만 계산하고 변경된 RawRecord를 마지막에 한 번 생성했다.
- 원시 위치 0의 단일 글자 모양 레코드는 경계 iterator·closure 없이 동일한 TextRun을 만들었다.
  빈 텍스트·잘못된 위치·런 예산 소진은 일반 경로를 유지했다.
- 컨트롤·책갈피가 없는 문단은 본문·서식·제목 처리 후 빈 객체 삽입 처리를 생략했다.

수정 후보는 `dochan/hwp/records/para_text.py`, `dochan/hwp/section.py`,
`tests/test_hwp_speed.py`였다. 공유 모듈과 다른 형식의 파서는 수정하지 않았다.
원복하며 보존한 diff는 `.codex-work/candidate.patch`, 후보 해시는
`.codex-work/candidate-source-sha256.json`에 별도 보존했다.

## 표본과 측정

공개 HWP 5,635개에서 크기·경로순 등간격 200개를 고정했다.
범위는 4,608–44,501,504바이트이고 100KB 미만 142개, 100KB–1MB 미만 38개,
1MB 이상 20개다. 공개 짝은 실제 발견된 press-pairs 91쌍을 사용했다
(예: `156783505`, `156783513`, `156783521`). 이전 시점의 코퍼스 건수를 재사용하지 않았다.

기준 소스는 수정 금지 round4 체크아웃이다. 같은 입력을 전·후·후·전·전·후로
측정한 각 3회의 중앙값이며, 초 단위다. 전체 HWP는 6개 작업자에서 파일별 파싱 시간의
합계를 기록했다. 표본은 Python 3.9.6과 3.12.12에서 각각 파싱만 측정했다.
가져오기 워밍업 이후 측정했고, CPU는 각 프로세스의 `process_time` 합계다.

| 대상 | 전 wall | 후 wall | 시간 변화 | 전 CPU | 후 CPU | CPU 변화 |
|---|---:|---:|---:|---:|---:|---:|
| HWP 전체 5,635개 / 3.9 | 301.918 | 313.372 | +3.79% | 134.540 | 122.863 | -8.68% |
| 표본 200개 / 3.9 | 34.952 | 30.005 | -14.15% | 10.352 | 9.075 | -12.33% |
| 표본 200개 / 3.12 | 14.802 | 11.683 | -21.07% | 6.346 | 5.593 | -11.87% |

장비의 동시 부하가 컸고, 같은 기준 소스도 회차에 따라 시간이 크게 달랐다.
따라서 위 wall 결과로 실제 성능 악화의 원인을 확정하지 않는다.
작업자는 목표 달성을 입증하지 못했다고 판단했으나, 유휴 장비 재측정에서 합류 조건을 충족했다(위 통합 재측정).

## 전후 프로파일

같은 200개에 `cProfile`을 적용하고 `pstats.Stats(..., stream=...)`로
self/cumulative 상위 60개를 각각 저장했다. 전후 인접 실행은
`profile-before-last-*.txt`, `profile-after-paired-*.txt`다.
첫 변경 전 프로파일 `profile-before-*.txt`와 초기 후보별 프로파일도 보존했다.
시간은 부하의 영향을 받으므로 호출 수 감소를 속도 합류의 대체 지표로 쓰지 않았다.

| 함수 | 전 호출 수 | 후 호출 수 | 전 self / cumulative (초) | 후 self / cumulative (초) |
|---|---:|---:|---:|---:|
| parse_para_text | 208422 | 208422 | 4.343 / 5.946 | 0.715 / 1.527 |
| _build_tree | 243 | 243 | 4.074 / 5.256 | 2.532 / 3.432 |
| _parse_paragraph_group_impl | 237512/158022 | 237512/158022 | 3.550 / 20.021 | 2.099 / 9.971 |
| _text_runs | 189857 | 189857 | 1.619 / 3.274 | 0.587 / 1.164 |
| struct.unpack_from | 5173071 | 2818100 | 0.693 / 0.693 | 0.371 / 0.371 |
| dataclass __init__ (전체) | 1648115 | 1351027 | 0.656 / 0.656 | 0.398 / 0.398 |

전체 호출은 84,622,869→59,073,990(약 30.2% 감소), dataclass 초기화는
1,648,115→1,351,027이었다. Python 호출·임시 객체 감소를 확인했지만
실제 전체 파싱 합계 목표로 연결되지는 않았다.

## 출력·동작 검증 (후보 최종 소스)

- 공개 8개 루트의 전 형식 14,491파일을 `scripts.probe_output_speed collect --workers 6`과
  `compare`로 검사했다. 가속 켬·끔 각각 Markdown·JSON·텍스트·진단 해시 차이 0,
  probe 수준 예외/timeout 0. 두 모드끼리, 켬의 반복 수집끼리도 차이 0이었다.
- 실제 형식별 파일 수: HWP 5,635, HWPX 2,683, PDF 2,064, DOC 490, DOCX 1,783,
  PPT 220, PPTX 544, XLS 720, XLSX 352.
- 공개 HWP↔HWPX 91쌍의 `scripts.compare_hwp_pairs` 결과 JSON은 전후 완전히 같았다.
  이는 기존 짝 차이를 없앴다는 뜻이 아니라 기존 대조 결과를 그대로 유지했다는 뜻이다.
- HWP에는 password 플래그 1개, distribution 플래그 28개, CFBError를 내는 12개가 포함됐다.
  이 파일들도 전수 해시·진단 비교에 포함했다. probe 예외 0은 손상 문서를 정상 파싱했다는 의미가 아니다.
- 원본 Python 구현과의 차등 검사: 텍스트 100,000(전체 WCHAR 값 포함), 트리 10,000,
  서식 런 100,000, 전체 문단 10,000, 총 220,000건. 전 필드·진단·예산·제목 등록 차이 0.
- 최적화 계약 4개가 기존 경로에서 실패하는 것을 먼저 확인한 뒤 후보에서 통과했다.
  관련 집중 검사 111 passed. 가속 켬 전체: `7291 passed, 39 skipped, 14 xfailed in 337.52s (0:05:37)`
  가속 끔 전체: `7281 passed, 49 skipped, 14 xfailed in 173.96s (0:02:53)`
- 최종 후보에 `ruff check dochan scripts tests setup.py` 통과.
  새 C 소스가 없어 신규 C의 ABI/ASan/UBSan 검증은 해당하지 않는다.
- 전 형식 각 2회 최솟값의 1.2배 초과 의심은 7,696개였다.
  작업자는 20회 재검사를 하지 않았고 이 수치로는 파일별 회귀 0을 주장하지 않는다.
  파일별 회귀는 오케스트레이터의 통합 재측정(1,047개, 10ms 이상 1.2배 초과 0건)이 근거다.

내부 문서는 사용·복사·기록하지 않았다. 코퍼스는 읽기 전용으로 사용했다.
README 지원 표·CHANGELOG·설정·빌드 등록 파일은 바꾸지 않았다.

## 재현 도구와 최종 상태

측정 스크립트·프로파일·상세 로그·해시 비교 집계는 `.codex-work/`에 있다.
`measure_hwp.py`, `benchmark.sh last`, `time_all_hwp.py full-last`, `last-collect.sh`,
`differential.py`가 각각 표본·교대·전체 합계·전 형식·차등 검사를 재현한다.
크기가 큰 원시 측정 JSON은 집계와 원자료 파일의 SHA-256을 남긴 뒤 정리했다.
집계는 `final-summary.json`에 보존했다.

작업자는 후보를 원복해 `candidate.patch` 로 보존했고, 오케스트레이터가 그 패치를 통합 가지에 적용해 채택했다.

## 제안

- 공유 모델의 `Document._find_recursive`와 공유 제목 판정(`utils/heading_font.py`)은
  여전히 상위 누적 비용에 나타났다. 문서 재귀 탐색과 반복 제목 계산의 재사용을
  별도 소유 작업에서 프로파일링할 가치가 있다. 이번 소유 범위에서는 수정하지 않았다.
- C 이식 전에 모델·트리·문단의 실제 객체 수 감소가 전체 합계로 이어지는지 먼저 확인한다.
