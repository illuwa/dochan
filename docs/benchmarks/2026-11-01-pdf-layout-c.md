# PDF 각주·미주·크기 런·본문 묶음 C 가속

## 범위와 동일성 계약

기준은 작업 시작 HEAD와 동일한 `base-round2`이다. 새 런타임 의존성 없이
CPython 3.9 제한 API 모듈 `_cnotes`, `_cheadings`, `_cbody`를 추가한다.
`DOCHAN_BUILD_ACCEL=1`에서만 빌드하며 `DOCHAN_DISABLE_ACCEL=1`이면 Python을 쓴다.
ImportError만 로더에서 처리한다. 실행 중 지원하지 않는 입력 및 C 예외는
예외 처리기 밖에서 Python 원본 계산을 재실행한다.

각주 전체를 C로 바꾼 것은 아니다. 가로 조각 분류와 각주 사전 판정, 미주 참조
기하 계산을 이식하고, 각주 모델 생성·경고·집합 병합·split marker 폭 변경은
기존 Python에 남겼다. 제목은 `sized_runs` 전체 루프를 옮겼지만 Unicode 연산과
`dataclasses.replace` 의미를 보존한다. 본문은 이벤트 분할만 C에서 준비하고
앵커 변경과 줄 조립은 Python에서 원래 순서로 수행한다. `merge_lines`는 변경하지 않았다.

| 단계 | 순서와 부작용 |
| --- | --- |
| 각주 | Counter 동률의 첫 등장, 안정 정렬, 정의 줄 순서, consumed set.update, 참조 dict 삽입 순서 보존 |
| 미주 | y 안정 병합 정렬, 인접 y/size 질의 재사용, 후보별 원래 기하 예산 소비와 경고 순서 |
| 크기 런 | 줄·런·조각 순서, zip의 짧은 쪽 길이, 반복 line 객체 identity, Unicode strip/find/isspace |
| 인접 크기 구간 | 같은 값이라도 새 size 객체로 교체하는 원본 동작 보존(int/float와 signed zero 포함) |
| 본문 | `(order, kind)` 안정 병합 정렬, 같은 order에서 표/경계가 조각보다 먼저, 빈 그룹 보존 |
| 표 앵커 | C는 읽기 전용 준비; 성공 시 원래 순서로 커밋, 실패 시 Python 재실행으로 예외 직전 부분 변경 재현 |

집합을 출력 순서의 원천으로 쓰는 곳은 없고, 사전 삽입은 결정적인 입력 목록
순서에 따른다. 따라서 Python 순서 결정화 변경은 필요하지 않았다. C의 산술은
`-ffp-contract=off`를 사용한다. 숫자 비교의 NaN identity shortcut, 크기 객체
교체, 문자 경계 의미를 별도 회귀로 확인한다. 큰 정수·비유한 기하·커스텀 객체
등 C가 보장하지 않는 입력은 Bailout한다.

## 구현 중 발견한 비용과 보완

본문 앵커를 찾는 중 각 y 객체를 임시 풀에 쌓으면 표 수×조각 수만큼 참조가
누적됐다. 비교 직후 해제하도록 바꿨다. no-match 2,000조각×500표를 두 번
호출하는 테스트에서 변경 전 약 8.6MB를 확인한 뒤, 변경 후 1MiB 미만을 확인했다.
제목 크기 사전은 실제 lookup만 필요하므로 매 문단 전체 사전 검증을 제거하고
조회한 키·값만 확인한다. 원본도 사용하지 않는 크기 값은 무시한다.

## 검증 방법

공개 PDF 2,281건의 Markdown·JSON·텍스트·진단 네 해시를 기준과 비교한다.
코퍼스 원본은 수정하거나 저장소로 복사하지 않는다. 실물 입력 캡처는 비추적
작업 폴더에서만 사용한다. 출력 동일성 검증은 문서 해석의 정확도를 새로
입증한다는 뜻이 아니다.

차등 비교는 타입, float IEEE 비트, 사전·집합 순회 순서, 모든 모델 필드와
일반 객체의 `__dict__`, 경고와 입력 변경을 포함한다. 공개 입력 원본과 순서
변경·중복·수치 경계·조각 누락·Unicode·크기 타입·제로 크기 변형을 비교한다.
C 직접 실행/성공 횟수도 별도로 세어 Python 폴백만 비교하는 것을 막는다.

성능은 correctness 검사를 끝낸 다음 단일 프로세스로 Python 3.9/3.12에서
전·후·후·전·전·후 순서의 300건 합계 중앙값을 구한다. 이어 전수 파일별
전후 각 2회 최솟값을 비교하며, 1.2배 이상 느린 10ms 미만 후보는 20회
중앙값으로 다시 판정한다. 이 문서의 합류 판정은 이 모든 조건을 사용한다.

### 10만 라운드 차등 검사

공개 입력 원본은 각주 160건, 제목 320건, 본문 160건이다. 이에 더해 각 단계
100,000개 변형을 검사했다. Python 3.12 최종 소스에서 각주 100,160,
크기 런 100,320, 본문 100,160, 미주 100,000회 비교의 결과·입력 변경·경고 차이가
모두 0이었다. 변형 안에서 실제 각주를 반환한 확인 횟수는 8,333회다.
크기 런 직접 C 차등 비교는 100,320회, 본문 직접 C 차등 비교는 100,160회이며,
각주 사전 판정 C 성공 104,700회, 가로 분류 C 성공 100,000회,
미주 C 성공 100,000회를 기록했다(추가 양성 확인 호출은 사전 판정 수에 포함).

입력 크기를 제한한 변형은 원본 전체 입력 검사와 구분한다. 각주는 최대 32조각,
본문은 최대 24조각·3표(+합성 빈 표), 제목은 최대 48세그먼트의 단일 줄이다.
본문 변형의 표 소비 order는 선택된 조각에 해당하는 부분집합으로 제한한다.
거대 입력 메모리 회귀는 별도 본문 테스트로 검증했다.

재현 도구와 원시 결과는 `.codex-work/capture-layout.py`, `fuzz-layout.py`,
`layout-inputs.pkl`, `fuzz-final.json`이다. 작업 폴더 캡처는 배포 산출물이 아니다.

ASan+UBSan에서도 위와 같은 비교 건수·C 성공 횟수·양성 각주 수로 차이 0,
산티타이저 진단 0을 확인했다. 3.9 헤더로 최종 세 C 소스를 빌드하고,
플랫폼 Python의 sanitizer 로딩 제한을 피하려고 Homebrew 3.13 framework의
실제 실행 파일에서 구동했다. 프로세스 전체 누수 검사는 끄고 메모리 접근과
정의되지 않은 동작을 검사했다. 다른 운영체제에서의 실행은 검증 범위가 아니다.
근거는 `sanitize-build.sh`, `run-sanitized.py`, `fuzz-asan.{log,json}`이다.

## 교대 3회 성능과 합류 판정

자체 correctness 검사와 병렬 해시 수집을 모두 종료한 뒤 실행했다. 단위는 초이며,
전·후·후·전·전·후 순서로 300개 파싱 시간 합계를 측정했다.

| Python | 기준 3회 | 후보 3회 | 기준 중앙값 | 후보 중앙값 | 단축률 |
| --- | --- | --- | ---: | ---: | ---: |
| 3.9.6 | 6.0271 / 6.1653 / 6.2022 | 5.9949 / 6.0618 / 6.2710 | 6.1653 | 6.0618 | 1.68% |
| 3.12.12 | 5.1675 / 5.8647 / 5.8054 | 5.2798 / 5.5431 / 5.7204 | 5.8054 | 5.5431 | 4.52% |

| Python | 전수 파일 | 2회 최솟값 회귀 후보 | 10ms 미만 20회 재검사 | 최종 1.2배 회귀 |
| --- | ---: | ---: | ---: | ---: |
| 3.9 | 2,281 | 98 | 52 | 47 |
| 3.12 | 2,281 | 156 | 93 | 64 |

3.9의 최종 회귀는 기준 10ms 이상 46건과 작은 파일 재검사에서 남은 1건이다.
3.12는 각각 63건과 1건이다. 규칙대로 10ms 이상 후보는 두 번 최솟값으로 판정하며
이를 추가 재측정으로 제외하지 않았다. 예를 들어 3.9 `bug1992868.pdf`는
236.673→360.289ms, `156783697.pdf`는 10.195→14.785ms였다.
작은 파일 `156781635.pdf`는 20회 중앙값도 5.108→7.968ms였다.
3.12 `issue8795_reduced.pdf`는 13.746→28.107ms였다.

호스트 전체 프로세스 부하 조회는 sandbox가 `ps`를 차단하여 확인하지 못했다.
특히 3.12 기준 세 번의 변동도 크므로 측정된 전체 차이를 모두 C 이식의 효과로
단정하지 않는다. 이 한계를 회귀를 제외하거나 합류 조건을 완화하는 근거로 쓰지 않았다.

**판정: 정확성·안전성 검사 통과, 성능 합류 보류.** 두 Python 모두 목표 10%에
미달하고 파일별 회귀가 남았다. 각주 전체의 C 이식이나 줄 조립 자체의 대폭 축소를
완료했다고 주장하지 않는다. 이 후보는 요청한 경계의 일부 계산을 C로 옮긴 미커밋
검토용 변경이며, 성능 합류 조건을 통과한 변경으로 취급하지 않는다.

원시값과 실행기는 `.codex-work/timing.py`, `timing.log`, `timing-summary.json`,
`time-*.json`, `all-time-*.json`, `small-time-*.json`이다.

## 단계 경계 계측과 한계

속도 판정 후 별도로 함수 경계 타이머를 넣어 같은 300건을 한 번씩 실행했다.
교대 중앙값과 혼합하지 않는다. 각주·미주·가로 분류·본문은 각각 840회,
크기 런은 6,115회로 기준/후보 호출 횟수가 같다. 단위는 초다.

| 단계 | 3.9 기준→후보 | 3.12 기준→후보 |
| --- | ---: | ---: |
| 가로 조각 분류 | 0.0562→0.0253 | 0.0339→0.0370 |
| 각주 검출(줄 조립 포함) | 0.3312→0.3193 | 0.2665→0.2647 |
| 미주 참조 | 0.1349→0.0904 | 0.1038→0.0869 |
| 크기 런 | 0.2392→0.1467 | 0.1476→0.1133 |
| 본문 묶음(줄 조립 포함) | 0.4247→0.2314 | 0.1427→0.1371 |
| 계측 실행 전체 | 5.7134→5.6040 | 4.2882→4.2141 |

각주 사전 계산을 C로 옮겨도 각주 검출 비용은 거의 줄지 않았다. 원래 프로파일과
구현 모두 이 단계에 줄 조립 비용이 남는 것을 보여준다. 크기 런은 Unicode 처리와
모델 `replace`, 본문 묶음은 `assemble_lines`를 유지한다. C 루프 이식만으로 이 비용을
제거한 것은 아니다. 3.12 가로 분류는 이 단발 계측에서 오히려 늘었다.

3.9 단계별 절감 합계는 전체 절감과 일치하지 않으며, 다른 단계 비용·GC 시점·호스트
변동 중 무엇이 얼마나 작용했는지 이 계측만으로 확정할 수 없다. 특히 본문 묶음의
큰 단발 차이를 반복 측정의 보장된 개선으로 사용하지 않는다. 파일별 회귀의
개별 원인도 모두 특정한 것은 아니다. 더 큰 개선은 아직 남은 줄 조립/모델 생성
비용을 다뤄야 하며, 현재 결과는 그 후속 구현을 완료했다는 증거가 아니다.
근거는 `.codex-work/stage-share.py`, `stages-{39,312}-{before,after}.json`이다.
