# PDF 내용 스트림 해석기 핵심의 선택적 C 가속, 그리고 세 가속을 합친 결과

2026-10-06. C 스캐너(`2026-10-06-pdf-content-scanner-c.md`) 다음 병목이던 해석기 루프·경로 수집·객체 파싱을 C 로 옮기고,
같은 날 만든 줄 조립 가속(`2026-10-06-pdf-line-assembly-c.md`)과 한 브랜치로 합쳐 다시 쟀다. 기본 배포물은 바뀌지 않는다.
세 모듈 모두 `DOCHAN_BUILD_ACCEL=1` 일 때만 빌드되고, 없거나 `DOCHAN_DISABLE_ACCEL=1` 이면 순수 Python 으로 동작한다.
이 문서에 README 기능 칸은 배정되지 않았다.

## 왜 여기였나

C 스캐너만 켠 상태에서 공개 PDF 300개(13.4초)를 단계별로 쟀다(벽시계, 소거법).

| 단계 | 시간 | 비중 | 이번 작업 |
| --- | ---: | ---: | --- |
| 글자 그리기·디코딩·폭 계산(`_show`) | 2.16초 | 16.1% | 그대로(Python) |
| 해석기 루프·그래픽/텍스트 상태 | 1.95초 | 14.5% | C (`_cinterp`) |
| 줄 조립 | 1.84초 | 13.7% | C (`_clines`) |
| 링크·각주·주석·반복 머리글 | 1.74초 | 12.9% | 그대로 |
| 표 복원 | 1.27초 | 9.4% | 그대로 |
| 경로 수집 | 1.17초 | 8.7% | C (`_cinterp`) |
| 문자열·배열·이름 객체 파싱 | 1.14초 | 8.5% | C (`_cinterp`) |
| 스캐너 | 0.95초 | 7.1% | 이미 C (`_cscan`) |
| 글꼴 준비·파일 구조·기타 | 1.29초 | 9.6% | 그대로 |

## 무엇을 만들었나 (`dochan/pdf/_cinterp.c` 와 헤더 둘)

- 손으로 쓴 C, CPython 제한 API(`Py_LIMITED_API 0x03090000`), 부동소수 연산 합성 금지(`-ffp-contract=off`, MSVC `/fp:precise`).
  코드 생성기와 다른 PDF 엔진의 코드는 쓰지 않았다.
- C 가 `q Q cm BT Tf Tc Tw Tz TL Tr w Td TD Tm T*` 와 경로 구성·칠하기 연산을 순수 경로와 같은 순서·조건으로 실행하고,
  `Tj ' " TJ Do BDC BMC EMC gs BI` 에서만 Python 으로 돌아온다. 순수 경로와 가속 경로는 Form·marked content·글자 분기를 같은 메서드로 쓴다.
- 숫자마다 int/float 꼬리표를 들고 Python 과 같은 규칙으로 계산한다. 행렬 곱은 상수 1·0 과의 곱셈까지 같은 순서로 하고,
  int 결과의 -0.0 은 0 으로, 2^53 을 넘는 정수는 물러난다. `hypot` 은 차이 하나가 0 이면 절댓값, 아니면 Python `math.hypot` 을 부른다.
- 문자열·16진 문자열·이름·평평한 배열은 `PDFLexer` 와 결과가 같다고 볼 수 있는 꼴만 C 에서 만들고 나머지는 그 위치에서 `PDFLexer` 에 맡긴다.
- 정확히 재현할 수 없는 입력(피연산자가 모자라거나 숫자가 아닌 연산자, 큰 정수, 비유한 값 등)을 만나면 `Bailout` 으로 그 페이지를
  순수 Python 으로 처음부터 다시 해석한다. 공개 300개에서 해석 호출 947회 중 2회(0.2%)였다.

## 독립 감수에서 나온 결함과 수정

구현(Codex)과 별도로 Opus 가 C 세 파일과 Python 쪽 연결을 감수했다. PDF 내용만으로 닿는 메모리 안전·참조 계수 결함은 찾지 못했고,
아래를 고쳤다.

| 발견 | 심각도 | 수정 |
| --- | --- | --- |
| 중첩 Form 에서 물러날 때마다 자식이 다시 C 부터 시도해 깊이마다 작업이 두 배. 3KB PDF 가 순수 0.003초, 가속 9초(깊이 16), 잎에 글자 2,000개를 넣은 깊이 12 는 336초 | 높음 | 물러나기를 페이지 최상위에서만 한다. 자식의 `Bailout` 은 그대로 올려 보내고(`_invoke_form` 의 `except Exception` 앞에서 재전파), 최상위가 새 문맥으로 순수 경로를 한 번 돈다. 깊이 16 의 해석 호출 131,071회 → 가속 17 + 순수 17회, 재현 PDF 0.002초·0.07초 |
| Form 호출마다 공유 문맥(`cache` 포함)을 통째로 복사 — Form 32,000개에서 가속이 순수보다 4.6배 느림 | 낮음 | 위 구조 변경으로 스냅숏·복원 자체가 없어졌다 |
| 경로 연산이 피연산자 수 64 를 직접 확인하지 않음. 내부 리스트를 `gc.get_referents` 로 찾아 늘리면 스택 버퍼 넘침(ASan) | 중간 | 복사 전에 수를 확인해 `Bailout`, 리스트 원소가 NULL 인 경우 전파. PDF 바이트만으로는 닿지 않는 경로였다 |
| `tp_traverse` 가 힙 타입을 방문하지 않음 | 낮음 | 방문 추가 |
| `paths.MAX_SEGMENTS` 가 2^63 이상이면 `OverflowError` | 낮음 | `Bailout` 으로 |
| 행렬 속성 대입이 실패하면 일부만 바뀐 채 남음 | 낮음 | 임시 배열에 검증한 뒤 복사 |
| `next()` 한 번이 긴 스트림에서 신호 처리를 막음(32MB 에서 0.15~0.3초) | 낮음 | 연산자 1,024개마다 `PyErr_CheckSignals()` |
| 모듈 초기화 실패 경로가 가져온 전역 참조를 놓지 않음 | 낮음 | 공통 정리 지점으로 |
| 물러난 뒤 순수 경로의 예외에 `Bailout` 이 `__context__` 로 붙음 | 낮음 | 재실행을 `except` 밖에서 |

감수와 별도로 엄격한 컴파일 점검에서 하나를 더 찾았다. 줄 조립 C 가 Python 3.9 제한 API 헤더에 없는 `PyMem_Calloc` 을 써서,
3.9 로 빌드하면 컴파일이 실패하고 optional 확장이 조용히 빠졌다(3.11 헤더로만 빌드해 확인했기 때문). `PyMem_Malloc` + `memset` 으로 바꿨고,
세 C 소스 모두 3.9 헤더에서 `-std=c99 -Wall -Wextra -Wpedantic -Werror` 를 통과한다.

## 속도

### dochan 자체 (PDF 2,362건, Xcode Python 3.9.6, 작업자 8, 교대 3회의 문서별 파싱 합계)

| 구성 | 1회 / 2회 / 3회 (초) | 중앙값 |
| --- | --- | ---: |
| 순수 Python — 리팩터 전(C 스캐너 가지, 가속 끔) | 296.2 / 301.4 / 300.0 | 300.0 |
| 순수 Python — 리팩터 후(이 가지, 가속 끔) | 308.4 / 302.9 / 298.8 | 302.9 |
| 세 가속 모두 켬 | 110.8 / 112.0 / 111.8 | 111.8 |

가속을 모두 켜면 순수 경로의 2.71배다. 공용 메서드로 뽑아낸 순수 경로는 중앙값이 1.0% 느리게 나왔는데 세 번의 범위가 서로 겹친다
(296~301초 대 299~308초). 느려졌다고도, 그대로라고도 단정하지 않는다.

### 다른 도구와 (공개 PDF 300개, Python 3.12.12, 교대 3회 중앙값, 두 도구가 모두 성공한 파일만 합산)

| 상대 도구 | 상대 시간 | dochan 순수 Python (20.2초) | dochan 세 가속 (8.1초) |
| --- | ---: | --- | --- |
| PyMuPDF `get_text()` | 2.4초 | 8.5배 느림 | 3.5배 느림 |
| pypdf | 23.7초 | 1.2배 빠름 | 3.0배 빠름 |
| pdfminer.six | 37.8초 | 1.9배 빠름 | 4.8배 빠름 |
| pdfplumber | 45.6초 | 2.3배 빠름 | 5.6배 빠름 |
| markitdown | 53.1초 | 2.7배 빠름 | 6.9배 빠름 |

회차별 합계는 dochan 순수 19.3 / 20.4 / 20.2초, 세 가속 7.6 / 8.4 / 8.1초이고, PyMuPDF 대비 배수는 3.47 / 3.47 / 3.38 이다.
파일별로는 중앙값 4.9 → 4.0ms, p95 180 → 68ms, 최대 3.43 → 1.34초다. dochan 은 300개 모두 성공했고 다른 도구는 2~5개씩 실패했다.

이 표를 잰 뒤 세 모듈이 호출마다 C 문자열로 Python 문자열을 새로 만들던 것(속성 이름·사전 키·방향 문자열)을 모듈 초기화 때 한 번
만들어 쓰도록 바꿨다. 줄 조립만 다시 흘린 시간이 2.44 → 0.68초(공개 400개의 조각 125만 개, 중앙값), 공개 300개 파싱 합계가
19.10 → 17.21초(Python 3.9, 교대 3회 중앙값)가 됐다. 그 빌드로 dochan 과 PyMuPDF 만 일곱 번 교대로 다시 쟀다.

| | 7회 (초) | 중앙값 |
| --- | --- | ---: |
| dochan 세 가속(문자열 캐시 뒤) | 7.00 / 6.89 / 6.96 / 7.16 / 7.07 / 6.92 / 7.00 | 7.00 |
| PyMuPDF `get_text()` | 2.27 / 2.25 / 2.25 / 2.26 / 2.37 / 2.25 / 2.26 | 2.26 |

회차별 배수는 2.99~3.16 이고 중앙값은 **3.09배 느림**이다(순수 Python 은 8.5배). 이 측정 때 장비에는 다른 작업의 부하가 있었고
(load average 8~10), 나머지 도구는 이 빌드로 다시 재지 않았다 — 위 표의 "빠름" 배수는 캐시 전 빌드 기준이라 조금 보수적이다.

PyMuPDF 의 `get_text()` 는 글자만 뽑는다. dochan 이 하는 일에 가까운 것을 시키면 순위가 달라진다(같은 300개, 3회).

| PyMuPDF 에 시킨 일 | 3회 (초) | dochan 세 가속 7.0초 대비 |
| --- | --- | --- |
| `get_text("dict")` — 글꼴 크기·굵기·좌표 포함 | 5.52 / 5.70 / 5.63 | dochan 이 1.2배 느림 |
| `get_text()` + `find_tables()` — 표 복원 | 33.34 / 35.88 / 32.96 | dochan 이 4.8배 빠름 |

dochan 은 여기에 더해 제목·링크·각주·반복 머리글을 복원하고 Markdown 을 만든다. 출력 계약이 달라 어느 비교도 같은 일의 처리량 비교는 아니다.

## 확인하지 못한 것과 남은 결정

- macOS arm64(Xcode 3.9 는 universal2)에서만 빌드했다. Linux·Windows 는 미검증이다. CI 에 Linux 빌드와 백엔드 단언·전체 테스트 작업을
  추가했지만(`accelerators`, 3.9·3.13) 이 문서를 쓰는 시점에는 실행해 보지 못했다.
- 확장 전체를 sanitizer 로 돌리는 것은 macOS 시스템 Python 에서 막혀 있다(`Sanitizer load violates platform policy`). Homebrew 의 framework
  실행 파일을 직접 띄우면 돌릴 수 있어 그렇게 확인했지만, CI 에 상시 작업으로 넣지는 않았다.
- 32비트 x86 GCC 는 `-ffp-contract=off` 만으로 x87 초과 정밀도를 막지 못한다. 그런 빌드는 없고, 생기면 출력 비트가 달라질 수 있다.
- 가속 휠을 PyPI 에 올릴지(운영체제·CPU 별 빌드 행렬)는 결정되지 않았다. 올리지 않아도 소스 설치에서 `DOCHAN_BUILD_ACCEL=1` 로 빌드해 쓸 수 있다.
- 글자 그리기(`_show`)는 여전히 Python 이다. 위 "남은 시간" 표에서 가장 큰 덩어리다.
