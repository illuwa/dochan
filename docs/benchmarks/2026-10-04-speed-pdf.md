# PDF 순수 Python 변환 속도 측정

2026년 10월 4일 Apple M5 Pro·48GB, macOS 26.6.2, `/usr/bin/python3` 3.9에서 측정했다. 문서마다 별도 프로세스에서 `Dochan(path)` 파싱, 기본 Markdown, 기본 JSON 직렬화를 순서대로 실행했다. 최대 동시 작업자는 4개이고 문서당 제한은 120초다. 아래 초 단위는 프로세스 시작 시간을 제외한 세 단계의 합이다. 실행 간 OS 캐시와 호스트 부하가 같지 않으므로 전수 시간 차이를 독립적인 속도 보장으로 해석하지 않는다.

Markdown·JSON 본문은 저장하지 않았다. 각 문서의 세 단계 시간, 문자 수, Markdown·JSON·오류 목록의 SHA-256만 `.codex-work/`에 저장했다. 내부 실물은 파일명이나 개별 결과를 공개하지 않고 80건 집계로만 표시한다. 공개 상위 30개는 변경 전 첫 측정 기준으로 정하고, 각 버전에서 별도 프로세스 3회 실행의 중앙값을 사용했다.

## 출력 동일성과 선택한 변경

최종 코드에서 완료한 PDF 2,120개 모두 변경 전과 Markdown·JSON·오류 목록의 SHA-256이 각각 일치했다. 공개 2,040개와 내부 80개에서 불일치는 0건이다. `tests/test_pdf_speed_differential.py`는 무작위·경계 입력 5,000개 이상에서 기존 렉서의 위치와 토큰을 비교하고, 전체 토큰 스트림 3,000개 및 축 선분 5,000개 이상을 차등 비교한다.

- `read_token`의 바이트별 Python 반복을 미리 컴파일한 정규식의 `match`로 바꿨다. PDF 공백과 구분자만 경계로 쓰고, 문자열·이름·배열·사전·inline image 내부 해석은 기존 경로에 남겼다.
- `_axis_segment`는 비유한 좌표와 대각선을 먼저 걸러 선분 객체와 길이 계산을 줄였다. 기존 0.6pt 축 허용오차, 1pt 미만 규칙, 선분 수 상한은 그대로다.
- 공백·주석 전체를 정규식으로 읽는 시도는 대형 PDF 프로파일에서 `skip_whitespace` 시간이 늘어 최종 코드에서 제외했다. 폰트 폭은 이미 사전 조회이며, 글리프 디코더는 경고를 만들 수 있어 출력 보존 근거 없이 캐시하지 않았다.

검증 명령과 원시 측정 JSON은 `scripts/probe_speed_pdf.py` 및 `.codex-work/`의 `pdf-before.json`, `pdf-after-final-stable.json`, `pdf-after-profile-final.json`, `pdf-before-public.json`, `pdf-after-public-final.json`에 남겼다. 프로브는 코퍼스 경로를 명령 인자로 받고 본문을 디스크에 쓰지 않는다.
