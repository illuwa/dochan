# HWP↔HWPX 동등성 검증 (2026-09-24, dochan 1.5.1)

같은 문서를 HWP(바이너리)와 HWPX(XML)로 각각 저장한 짝을 두 리더로 읽어, HWPX 파서 결과를
정답지로 HWP 파서를 채점한다. PDF 검증(`scripts/compare_pdf_pairs.py`)과 같은 원리이며, 바이너리
레코드 배치를 잘못 알고 있어도 단위 테스트(같은 믿음으로 만든 픽스처)로는 잡히지 않는 결함을 잡는
유일한 방법이다.

## 자료

- `test_pairs/` (저장소 밖): 동일 문서 HWP/HWPX 짝 **76개** (무역안보관리원 규정·지침·계획 문서,
  HWP 5.0 한컴 저장본). PDF 검증에 쓰는 79쌍과 같은 집합에서 `.hwp` 가 있는 것.
- 내부 실물 문서 **2쌍**(별도 디렉터리, 파일명·내용 비공개): 경영평가 편람(중첩 표 42개, 표 156개)과
  점검 양식(대형 표 4개). 아래 표에 "내부" 로만 적는다.

## 실행

```bash
python -m scripts.compare_hwp_pairs test_pairs/ --output out.json
python -m scripts.compare_hwp_pairs <내부 디렉터리> --output out-internal.json
```

지표: `tok_ratio`(플레인 텍스트 공백 토큰 시퀀스의 difflib 유사도), `hwpx_tables`/`hwp_tables`,
`signature_match`(행·열·병합 서명 정확 일치 / 정답 표 수), `mean_cell_hit`(정답 셀 텍스트 적중률),
`hwpx_nested`/`hwp_nested`/`nested_match`, `mean_format_match`(텍스트로 짝지은 본문 문단 중
(텍스트, bold, italic) 런 시퀀스까지 같은 비율), `pairs_with_errors`.

토큰 유사도·셀 적중률이 내려간 짝은 없다. 남은 차이: 표 1개(76쌍)는 HWPX 쪽 서식 표 하나가 HWP 에서
다른 구조로 저장된 경우이고, 텍스트 유사도 잔차(≤ 0.7%)는 책갈피 마커·필드 표기 차이다.

## 찾은 결함과 원인

1. **`PARA_CHAR_SHAPE` 6바이트 오독** — 실제는 (UINT32 위치, UINT32 ID) 8바이트 쌍. 실물 레코드
   `00000000 0a000000 0d000000 09000000` = (0, 10), (13, 9). 6바이트로 읽으면 `(0,10),(983040,0)` 같은
   쌍이 나와 위치가 감소하고, `text[pos:end]` 슬라이스가 겹쳐 문단 뒷부분이 최대 3번 중복됐다(76쌍 중
   74쌍 영향). 위치 단위는 제어문자를 폭대로 센 원시 WCHAR(확장 컨트롤 = 8)이다: 24자 문단 + 확장
   컨트롤 2개에서 두 번째 구간이 32 = 24 + 8 에서 시작했다.
2. **중첩 표 평탄화** — `_parse_cell_info` 가 셀 안 `Table` 을 문단으로 풀었다. 초기 커밋부터 있던
   동작으로, HWPX 리더와 출력이 달랐다.
3. **비압축 BinData** — 압축 문서에서도 PNG/JPEG 는 원본으로 저장된다. `zlib.error` 가 `ValueError`
   분기에 잡히지 않아 문서 전체 이미지 연결이 중단됐다.

## 한계

- `format_match` 는 bold/italic 만 본다(밑줄·크기·색은 제외).
- 76쌍은 한 기관의 규정류 문서라 표 스타일이 비슷하다. 공개 코퍼스(7,076건)에는 HWPX 짝이 없어
  이 방법을 적용할 수 없다.
