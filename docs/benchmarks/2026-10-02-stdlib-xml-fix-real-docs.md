# 표준 라이브러리 XML 전환 5차 리뷰 실물 검증

2026년 10월 3일에 lxml 기반 커밋 `5a56b21`과 4차 결과를 기준으로 공개 문서의 Markdown, JSON, 오류 목록을 비교했다. 같은 문서를 Python 3.9와 `PYTHONHASHSEED=0`으로 읽고 각 출력의 UTF-8 SHA-256과 바이트 수만 저장했다. 대형 XLSX는 출력 전문을 만들지 않고 순차 해싱했다. 코퍼스 파일은 읽기만 했다. 이 수정은 README Supported Elements의 새 칸을 구현하지 않는다.

일반 API로 확인한 5,419개 중 5,418개가 기준본과 같았다. 대형 XLSX 한 건을 별도 확인한 뒤 전체 5,420개 중 5,419개가 같았다. 유일한 차이는 `corpus/poi-src/test-data/spreadsheet/LIBRE_OFFICE-116306-0.xlsx`다. 이 파일의 한 시트는 XML 요소 수 상한을 넘는다. 기준본은 워크북 전체를 비웠고, 수정본은 해당 시트에 오류를 기록하면서 다른 정상 시트의 표를 남겼다. 이는 시트 단위 격리 요구에 따른 개선이며 출력 동일성으로 세지 않았다.

5차 결과와 4차 결과는 공개 5,420개 모두에서 같다. 일반 API 5,419개의 Markdown·JSON·오류 해시가 같고, 별도 순차 해시를 낸 대형 XLSX 한 건의 출력 바이트 수와 해시도 같다.

`poc-shared-strings.xlsx`의 Markdown은 12,579,810,358바이트, SHA-256은 `660ed23976190164526b13a390b5d9ec51cbb75c22db26aa67c1c90abd7a2123`이다. JSON은 37,760,638,086바이트, SHA-256은 `3bc48e753a20af3655b6ccd966915bf88cddf3d1cbcab2b9f367af7d92269e13`이다. 두 출력과 오류 목록의 해시가 기준본과 같다.

## 리뷰 결함 검증

| 지적 | 합성 입력과 정답 근거 | 수정 후 실제 | 판정 |
|---|---|---|---|
| 큰 속성 및 UTF-16 | 24MiB 단일 속성, 3MiB `o:gfxdata`, UTF-16 한글 속성과 1,500개 속성을 합성했다. lxml은 큰 속성을 읽는다. | `fromstring`과 `iterparse`가 같은 값을 읽고 파트 크기 상한은 유지한다. | 단위 테스트를 통과했다. 같은 크기의 공개 실물은 확인하지 못했다. |
| DTD 내부 부분집합 | 주석 속 대괄호와 64KiB 초과 본문·주석·인용 값을 합성했다. | 작은 선언은 정화하고 64KiB 초과 내부 부분집합은 파트 오류로 처리한다. | 단위 테스트를 통과했다. |
| VML 대체 스캐너 | 주석·CDATA·처리 명령의 가짜 이미지, 닫히지 않은 주석, 다수의 일반 태그 속성을 합성했다. | 실제 `imagedata`만 추출한다. 일반 태그에서는 실제 `xmlns` 속성만 찾고 대체 경로 입력을 1MiB로 제한한다. | 단위 테스트를 통과했다. |
| XLSX 손상 시트 | 완료 행 두 개 뒤에서 닫는 태그가 끊긴 작은 시트와 정상 시트를 한 파일에 넣었다. | 완료 행 두 개와 정상 시트를 모두 보존하고 손상 시트 오류를 남긴다. | 단위 테스트를 통과했다. 같은 손상 형태의 공개 실물은 미검증이다. |
| XLSX 선택적 파트 | 정상 셀과 바닥글에 손상된 시트 관계 또는 댓글 파트를 붙였다. | 셀과 바닥글을 유지하고 선택적 파트 오류만 기록한다. | 단위 테스트를 통과했다. 같은 손상 형태의 공개 실물은 미검증이다. |
| XLSX 과대 시트 | 시트 파트 한도를 낮춘 합성 워크북으로 과대 시트와 정상 시트를 함께 만들었다. | 과대 시트 오류를 기록하고 정상 시트를 보존한다. 기존 파트 크기 상한은 그대로다. | 단위 테스트를 통과했다. 실제 101MiB 손상 짝은 미검증이다. |
| Python 3.13 스트리밍 종료 | 잘린 시트의 완료 행 뒤에 `XMLPullParser.close()` 오류가 나는 입력을 사용했다. | 종료 오류를 전파하기 전에 완료 이벤트를 비워 행을 보존한다. | Python 3.13 단위 테스트 5건을 통과했다. |

앞선 회차에서 추가된 256KiB 시작 태그와 1,024개 속성의 사전 검사 단언은 정상 대형 속성 입력을 잘못 거부했다. 이 단언을 파트 크기 상한 및 실제 속성 출력 계약으로 정정했다. 작은 손상 시트에서 완료 행이 없다는 단언도 데이터 손실을 고정하므로 완료 행 보존으로 정정했다. 두 경우의 이유와 실패·통과 테스트는 작업 보고서에 기록했다.

5차 리뷰에서 VML 태그의 백트래킹 정규식을 선형 스캔으로 바꾸고, 속성 값 안의 `xmlns` 문자열을 선언으로 보지 않도록 속성 경계를 추적했다. BOM 없는 UTF-16 LE/BE VML 이미지와 1바이트씩 읽히는 EUC-KR XML 선언을 합성 입력으로 검증했다. ZIP CRC가 손상된 XLSX 시트 관계 파트도 합성 파일로 확인했으며, 정상 셀을 유지하고 관계 기능의 오류만 기록한다. 이 손상 형태와 인코딩 경계의 공개 실물 표본은 확인하지 못했으므로 별도의 ✅ 근거로 사용하지 않는다.

| 5차 지적 | 합성 입력의 기대 | 실제 | 판정 |
|---|---|---|---|
| VML 종료 없는 태그 | 8MiB 입력을 강제로 대체 경로에 넣어도 메모리가 입력 크기 수준이어야 한다. 기본 한도는 1MiB여야 한다. | 최종 코드의 8,388,608바이트 입력에서 `tracemalloc` 최고 16,800,578바이트, 최대 RSS 51,920,896바이트였다. 기본 한도는 1MiB다. | 통과했다. |
| 속성 값 속 `xmlns` | 실제 네임스페이스 선언이 없으므로 가짜 이미지는 0개여야 한다. | 가짜 이미지가 0개다. | 통과했다. |
| 관계 파트 CRC 손상 | `A1=7`을 유지하고 관계 기능 오류를 기록해야 한다. | 셀 값 `7`과 CRC 오류를 함께 얻었다. | 통과했다. |
| BOM 없는 UTF-16 VML | LE와 BE 각각 실제 이미지 1개여야 한다. | 두 인코딩 모두 이미지 1개다. | 통과했다. |
| 짧은 스트림 읽기 | XML 선언이 1바이트씩 도착해도 EUC-KR `한글`을 읽어야 한다. | `한글`을 읽었다. | 통과했다. |

태그별 속성 수의 구조 상한은 추가하지 않았다. OOXML XML 파트는 32MiB, HWPX XML 파트는 32MiB, 일반 `fromstring` 입력은 100MiB의 크기 상한을 적용한다. 속성 수가 많으면 그 상한 안에서도 큰 메모리가 필요할 수 있다. 앞선 감수에서 51MiB와 약 400만 속성을 사용한 직접 파서 측정은 수정본 최대 RSS 1,784MiB, lxml 1,921MiB였다. 이는 속성 수별 독립 상한이 없는 계약과 메모리 비용을 명시하기 위한 측정이며, 일반 문서의 메모리 사용량을 뜻하지 않는다.

## 성능

기준본은 `5a56b21`에서 만든 소스 스냅숏이며 주요 리더 파일이 해당 커밋과 바이트 단위로 같음을 확인했다. DOCX, PPTX, HWPX 공개 문서 4,043개를 네 작업자로 각각 세 번 처리했다. 회차마다 파일 순서를 시드 41, 73, 109로 섞었다. 각 문서의 읽기·Markdown·JSON·오류 해시 시간 최솟값을 형식별로 합산했다. 각 회차의 4,043개 출력 해시가 모두 기준본과 같았다.

| 형식 | 표본 수 | lxml 기준본 최솟값 합(초) | 수정본 최솟값 합(초) | 변화 | 판정 |
|---|---:|---:|---:|---:|---|
| DOCX/DOCM | 1,794 | 13.7991 | 15.7706 | +14.29% | +20% 이내다. |
| PPTX/PPTM | 549 | 3.0907 | 3.2855 | +6.30% | +20% 이내다. |
| HWPX | 1,700 | 59.9186 | 62.0178 | +3.50% | +20% 이내다. |

4차 프로파일에서 XML 트리 생성 중 매 요소에 호출되는 `_BoundedTree.start`와 `end`가 주요 추가 비용이었다. 당시 DOCX 표본 100개의 파싱에서 `_parse_tree` 누적 0.375초 중 `start`가 0.148초였고, PPTX 표본 100개에서는 0.696초 중 0.350초였다. 4차에는 네임스페이스 범위 지도가 필요 없는 문서에서 그 지도를 쌓고 비우는 작업을 생략했다. 5차 첫 재측정에서 DOCX가 +23.05%로 목표를 넘었으므로, 같은 경로에서 불필요한 네임스페이스 분기까지 제외하는 `_PlainBoundedTree`를 추가했다. 최종 재측정은 표와 같다. 남은 상위 비용은 XML 트리 생성, JSON 인코딩, 문서별 요소 변환이다. 성능 수치는 이 호스트의 관측값이다.

## 재현

코퍼스 루트는 명령 인자로 전달한다. 출력 전문은 저장하지 않는다.

```sh
PYTHONHASHSEED=0 /usr/bin/python3 -m scripts.probe_stdlib_xml_migration corpus --source . --workers 4 --exclude poi-src/test-data/spreadsheet/poc-shared-strings.xlsx --output result.jsonl
/usr/bin/python3 -m scripts.probe_stdlib_xml_migration --compare baseline.jsonl result.jsonl
PYTHONHASHSEED=0 /usr/bin/python3 -m scripts.probe_stdlib_xml_migration --source . --stream-file corpus/poi-src/test-data/spreadsheet/poc-shared-strings.xlsx --output stream-summary.json
PYTHONHASHSEED=0 /usr/bin/python3 -m scripts.probe_stdlib_xml_migration corpus --source . --workers 4 --formats docx pptx hwpx --shuffle-seed 41 --output performance-41.jsonl
/usr/bin/python3 -m pytest tests/ -q -p no:cacheprovider --basetemp=.codex-work/pytest-tmp
```
