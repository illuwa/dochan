# PDF 문서 객체 파서의 선택적 C 가속

2026-11-01. 기준 소스는 시작 커밋 `d9683a9`의 기존 detached 체크아웃이다.
문서 객체 파서와 ObjStm 일괄 파싱만 변경했으며, 내용 해석기·표·각주·리더는 변경하지 않았다.
새 런타임 또는 빌드 의존성은 없다. 손으로 작성한 CPython 3.9 제한 API 확장이다.

## 구현과 동일성 계약

- `_cobjects.c`: 공백·주석·토큰, 이름, 숫자/참조, 리터럴/16진 문자열, 중첩 배열/사전,
  간접 객체 헤더와 stream 시작/끝 경계를 처리한다. `/Length` 해석 콜백은 Python에서 한 번만 호출한다.
  이스케이프 없는 이름은 입력 버퍼에서 바로 디코딩하고, 보통 십진 소수는 CPython과 같은
  `PyOS_string_to_double`로 변환하여 임시 bytes 객체와 타입 호출을 없앴다.
- 성공할 때만 값·위치·짝 없는 닫힘 괄호 수를 반영한다. 모르는 토큰·불완전 입력·방어 상한은
  `Bailout` 후 원래 Python 파서로 원래 위치부터 한 번 재실행한다. 중첩 자식에서 C를 다시 시도하지 않는다.
  Python 예외에 `Bailout` 문맥을 붙이지 않는다.
- `_PythonPDFLexer`와 `_parse_indirect_python`을 차등 기준으로 남겼다.
  Python의 숫자 처리, 이상한 이름 이스케이프, 음수 인덱싱, 한도 예외와 최종 위치를 보존한다.
- ObjStm의 헤더 및 객체들을 한 C 호출에서 파싱한다. 번호가 아닌 오프셋으로 결과를 보관하여
  중복 번호의 첫 일치 및 xref 인덱스 대체 동작을 유지한다. 실패한 객체의 진단은 실제 요청 때만
  원래 경로에서 만든다. 사용하지 않는 손상 객체는 경고를 추가하지 않는다.
- C 재귀는 64단계, 일괄 처리에는 바이트 작업 예산을 두고 초과분은 지연 Python 경로로 넘긴다.
  중첩·겹치는 오프셋의 중복 작업 및 거대한 `/First` 값도 회귀 테스트한다.
- `DOCHAN_BUILD_ACCEL=1`일 때만 빌드, `DOCHAN_DISABLE_ACCEL=1`로 해제한다.
  `ImportError`만 억제하고 `OBJECT_PARSER_BACKEND`로 실제 선택을 노출한다.
  sdist에 C 소스를 포함하고, 가속 휠 검증기는 `_cobjects` 및 네 번째 백엔드도 확인한다.

## 검증 범위

공개 코퍼스 실재 PDF는 **2,281건**이다. 작업서의 2,362건은 과거 기록에서 공개 2,281건과
내부 81건을 합한 숫자다. 내부 문서는 이번 실행에서 열거나 수록하지 않았다.

| 공개 묶음 | PDF 수 |
| --- | ---: |
| pdfjs-src | 983 |
| lo-src | 24 |
| press-pairs | 375 |
| press-pairs-holdout | 217 |
| press-pairs-holdout2 | 232 |
| press-pairs-holdout3 | 233 |
| press-pairs-holdout4 | 217 |
| 합계 | 2,281 |

`probe_output_speed`의 공개 경로 목록을 PDF로만 필터링하고, 같은 collect/compare 함수로
Markdown·JSON·일반 텍스트·진단 목록의 SHA-256을 대조한다. 손상 PDF의 WARN/ERR도
진단 목록 해시에 포함된다. 변환 성공은 내용 정확성을 보증하지 않으며, 여기서는 기존 결과와의
동일성만 검증한다. 속도와 무관한 휴리스틱을 조정하지 않았으므로 보류 코퍼스를 튜닝에 쓰지 않았다.

기존 테스트의 단언은 바꾸지 않았다. 휠 테스트의 정상 입력 fixture에 네 번째 모듈을 추가하고,
새 모듈 누락을 거부하는 별도 테스트를 넣었다.

중간 검증에서 순수 모드의 새 배치 테스트가 비어 있는 지연 캐시를 고려하지 않은 1건 실패가 있었고,
그 모드의 계약을 확인하도록 수정한 뒤 최종 전체 실행에서 통과했다.

## 성능 측정 과정

첫 고정 코드의 교대 3회 중앙값은 3.9에서 14.0852→12.6059초(-10.50%),
3.12에서 7.21228→6.64464초(-7.8705%)였다. 후자는 8% 목표에 못 미쳤다.
이 결과는 `.codex-work/candidate-1/`에 보존했다. 이름·십진 소수의 임시 할당을 줄인 뒤
동일성·안전성·성능 전체를 다시 검증했다. 최종 수치는 다음 표를 따른다.

| Python | 기준 3회(초) | 최종 3회(초) | 중앙값 전→후(초) | 감소 |
| --- | --- | --- | --- | ---: |
| 3.9.6 | 11.5329 / 11.3105 / 12.4610 | 10.0870 / 10.3258 / 11.7678 | 11.5329 → 10.3258 | **10.47%** |
| 3.12.12 | 7.1186 / 7.1550 / 6.9833 | 6.4633 / 6.3984 / 6.3451 | 7.1186 → 6.3984 | **10.12%** |

각 인터프리터에서 전·후·후·전·전·후 순서로 실행했다. 기준은 기존 세 PDF 가속을 켠 상태,
최종은 새 객체 가속까지 켠 상태다. 무거운 검증 작업을 모두 끝낸 뒤 측정했다.
두 버전 모두 중앙값 기준 8% 감소 목표를 충족했다. 회차 변동이 있으므로 소수점 수치를
다른 장비/부하의 보장값으로 해석하지 않는다.

| Python | parse_object 누적 전(초) | 누적 후(초) |
| --- | ---: | ---: |
| 3.9.6 | 2.523283 | 0.005219 |
| 3.12.12 | 2.735586 | 0.005089 |

위 누적 시간은 별도 cProfile 실행이다. C 진입점의 시간은 Python `parse_object` 항목에서
빠지므로 이 감소율을 전체 파싱 속도 향상으로 주장하지 않는다. 전체 성능은 앞 표를 따른다.

## 재현

`BASE`는 기준 체크아웃, `CORPUS`는 공개 코퍼스 루트, `PY312`는 별도 3.12 환경,
`PATHS`는 작업 시 제공된 공개 PDF 300개 JSON 경로 목록을 뜻한다.

```sh
DOCHAN_BUILD_ACCEL=1 python setup.py build_ext --inplace --force
python -m scripts.probe_pdf_objects --paths "$PATHS" --count 200000
python -m pytest tests/ -q -p no:cacheprovider
DOCHAN_DISABLE_ACCEL=1 python -m pytest tests/ -q -p no:cacheprovider
python -m ruff check dochan scripts tests setup.py
```

측정 원본과 실제 실행용 도우미는 `.codex-work/`에 남긴다. `collect_pdf.py`는
`probe_output_speed.collect_paths` 결과에서 `.pdf`만 선택하는 얇은 래퍼다.
`benchmark_rounds.py`는 각 인터프리터에 대해 전·후·후·전·전·후 순서를 실행한다.
각 회차는 새 프로세스에서 동일 300개를 `Dochan(path)`로 읽고 문서별 파싱 시간을 합산한다.
프로파일은 속도 측정과 별도로 실행한다. `parse_object` 프로파일 값만으로 모든 C 파싱 비용을
해석할 수는 없다. 간접 객체와 배치 경로는 C 안에서 해당 Python 호출을 제거하기 때문이다.

## 한계

macOS에서 검증했다. 다른 운영체제의 휠 및 CI 실행 결과는 이 기록에 포함하지 않는다.
산티타이저는 시스템 Python의 플랫폼 제한을 피하기 위해 Homebrew 3.13 framework 실행 파일에서
실행한다. Python 프로세스 전체의 누수 검사는 끄고 ASan 메모리 접근 및 UBSan 검사를 사용한다.
알 수 없는 입력과 방어 상한 초과 입력의 성능은 Python 폴백의 비용을 따른다.
