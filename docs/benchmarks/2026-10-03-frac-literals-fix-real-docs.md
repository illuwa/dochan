# 분수 리터럴 감수 후 공개 실물 검증

정답은 공개 Apache POI 표에 동봉된 Excel 표시 텍스트와 `NumberFormatTests.xlsx`의 `TEXT()` 저장값이다. 토큰 경로 검증은 표의 각 서식에 `[Red]` 접두와 빈 문자열 접미 `""`를 각각 붙여 수행했다. 이 접두와 접미는 분수 값과 표시 공백을 바꾸지 않으면서 기본 서식의 빠른 경로를 우회한다.

| --- | --- | --- | --- | --- | --- |
| XLS 날짜/숫자 서식의 분수 | `corpus/poi-src/test-data/spreadsheet/54686_fraction_formats.xls`, `54686_fraction_formats.txt` | 같은 공개 표의 Excel 표시 텍스트 3,540셀 | 토큰 경로 두 변형에서 공백 포함 3,540셀 일치 | `[Red]` 접두 3,540/3,540셀, 빈 문자열 접미 3,540/3,540셀 정확 일치했다. 두 변형 모두 공백 정규화 3,540/3,540셀이다. 기본 경로는 공백 정규화 3,540/3,540셀, 공백 포함 2,190/3,540셀이다. | 실물 검증 통과 |

고정 분모 `10`과 `100`의 `0`은 분모 자리표시자가 아니라 고정 숫자다. 토큰 경로에서 이를 자리표시자로 읽어 `110`과 `1100`으로 늘리던 오류를 고쳤다. 앞쪽 `_` 패딩은 정수부와 분자 사이의 패딩이 아니므로 가분수 선택 근거에서 제외했다. `#,##0 ?/?`와 `0.0 ?/?`처럼 분자 앞에 별도의 숫자 형식이 있는 형태는 이전 표시 경로를 유지한다. 분모의 `?` 정렬 공백은 공개 표와 같이 숫자 뒤에 둔다.

맨 `?/?`의 가분수 표기는 직접 대응하는 공개 캐시 행이 없으므로 이전의 혼합분수 표시로 되돌렸다. `00/00`은 이전의 0 자리 채움 결과를 유지한다. 정수부가 생략될 때 경계 공백은 공개 표의 공백과 캐시의 콜론 형태에만 적용한다. `# ? / ?`와 `# ?-/-?`는 토큰 경로에서 원시 값으로 후퇴하던 회귀를 막고 이전 표시로 되돌렸다. `# ?/?%`의 백분율 배율 미적용은 감수 전부터 있던 범위 밖 문제이며, 이 작업의 실물 검증에 포함하지 않았다.

재현 명령은 `python -m scripts.probe_xls_fraction_excel corpus/poi-src/test-data/spreadsheet --token-path --output <결과 파일>`이다. `DOCHAN_PUBLIC_SPREADSHEET_CORPUS=corpus/poi-src/test-data/spreadsheet python -m pytest tests/test_spreadsheet_fraction_review.py`로 3,540셀 회귀 테스트를 실행할 수 있다. 코퍼스가 없는 CI에서는 해당 테스트만 건너뛰며, 합성 회귀 테스트는 실행한다.

## 2차 감수 후속 검증

정수부 없는 고정 분모에서 정수 값이 분모로 한 번 더 나뉘던 오류를 합성 테스트로 재현했다. 검증된 `_` 패딩 가분수 이외의 형태는 종전 대분수 표시로 돌렸다. `???/100`의 `1.2 → 120/100` 단언은 직접 Excel 저장값이 없는 가분수 추정이므로 `1 20/100`으로 정정했다. `%`가 붙은 분수도 종전 표시로 돌아가며, 백분율 배율까지 맞춘다는 의미는 아니다. 분자와 슬래시 사이의 공백·기호는 하나의 규칙으로 종전 표시를 쓴다. `#/#`와 `##/##`의 Excel 표시값은 검증되지 않았다.

합성 서식 9,000개와 값 16개를 조합한 144,000개 입력을 CI 테스트로 실행한다. 토큰 경로에서 다시 숫자로 읽을 수 있는 출력 10,000개 이상에 대해 분모 한도에 따른 오차 안에서 값 오류 0건을 확인했다. 표시 직전에도 정수부·분자·분모를 다시 합산해 값이 맞지 않으면 기존 분수 표시로 되돌린다. 실물 코퍼스에는 이번 합성 가분수·백분율 경계 사례의 독립 Excel 정답이 없으므로 그 개별 표시의 Excel 일치 여부는 미검증이다.
