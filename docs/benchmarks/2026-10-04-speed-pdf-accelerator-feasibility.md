# PDF 컴파일 가속 타당성 조사

이번 조사는 2차 PDF 최적화 뒤 소스를 기준으로 한다. 가속 모듈을 제품에 넣거나 배포 설정을 변경하지 않았다. 프로토타입 소스와 바이너리는 `.codex-work/proto/`에만 있고, 커밋 대상은 측정 스크립트와 이 문서뿐이다. 이 조사에 README 기능 칸은 배정되지 않았으므로 새 체크를 제안하지 않는다.

## 측정 조건과 해석 범위

2026년 10월 4일 macOS 26.6.2, arm64, CPython 3.12.12, Apple clang 21.0.0에서 측정했다. mypy 2.4.0의 mypyc와 Cython 3.3.0을 사용했다. dochan과 PyMuPDF는 별도 도구 환경에서 같은 CPython 버전으로 실행했다. 호스트의 M5 Pro·48GB는 작업 지시의 환경 정보이며 CPU 명칭 조회는 샌드박스에서 거부됐다.

오케스트레이터가 제공한 공개 PDF 300개 목록을 그대로 사용했다. 공개 상위 30개는 기존 2차 전수 결과에서 느린 공개 문서를 골라 고정했다. 과거 상위 30개 표에는 내부 문서가 섞여 있지만 이번 조사에는 공개 문서만 쓴다. 이 집합의 상위 10개를 프로파일링했다. 목록을 `corpus/` 상대 경로로 바꾸고 각 경로 뒤에 LF를 붙여 SHA-256을 계산하면 300개 목록은 `54065a1963a417df16efb72907e353bac2ab51a2c233b30d10ec3b7aa5dcfcc0`, 상위 30개 목록은 `13778163492197b7c4c639e21382f7a1563e5ad03ea98d6ee81638a7eb72bb8c`다.

각 방식은 한 프로세스에서 import를 끝낸 뒤 파일 목록을 순서대로 변환한다. 첫 회와 셋째 회의 순서는 순수 Python→mypyc→C 스캐너→결합→PyMuPDF이고, 둘째 회는 역순이다. 다른 벤치마크를 동시에 실행하지 않았다. 표의 합계는 회차별 전체 합계 세 개의 중앙값이다. 파싱·Markdown·JSON의 실제 벽시계 시간을 사용했고 프로세스 시작, import, 해시 계산과 디스크 기록은 합계에서 제외했다. 파일당 제한은 120초다. 과거의 Python 3.9 문서별 독립 프로세스 측정과 직접 합산하지 않는다.

PyMuPDF는 일반 텍스트만 추출하고 dochan은 모델을 만든 뒤 Markdown과 JSON을 출력한다. PyMuPDF 대비 배수는 공통 성공 파일에서 dochan의 파싱+Markdown과 PyMuPDF의 텍스트 추출 시간을 비교한다. 이는 동일한 출력 계약의 처리량 비교가 아니며, PyMuPDF 출력과의 해시 일치를 주장하지 않는다.

본문을 저장하지 않고 Markdown·JSON·오류 목록 SHA-256과 문자 수·오류 수·시간만 기록했다. 코퍼스에 새 파일이나 변환 결과를 쓰지 않았다. 이번 집합은 프로토타입 의미 보존 검증이며 독립된 새 보류 집합이라고 주장하지 않는다.

## 단계별 비용과 조건부 암달 상한

현재 순수 Python 코드의 공개 상위 10개와 표본 300개를 각각 한 번 `cProfile`로 다시 실행했다. 함수의 누적 시간을 합산하지 않고 자기 시간만 합산했다. C 내장 함수는 직접 호출자별 자기 시간 비율로 귀속했다. 문자열·배열 파서는 객체 파싱, 스캐너 자체 메서드는 스캔, 내용 해석기의 나머지 분기와 경로 수집은 그래픽 상태·경로에 넣었다. 행 객체와 레이아웃은 줄·문단 조립에 넣었고, JSON 인코더와 `asdict`는 출력에 넣었다. 글꼴 자원 준비 등 명확히 분류하지 않은 비용은 기타에 남겼다.

이 분해는 단계 경계에서 잰 독립 벽시계 시간이 아니다. 직접 호출자만 쓰는 C 함수 귀속과 함수 단위의 분류에는 오차가 있다. 프로파일러 오버헤드도 호출이 많은 단계의 비중을 바꾼다. 아래 열은 각각 정확히 100%를 구성하지만 실제 처리시간의 엄밀한 상한으로 읽으면 안 된다.

암달 식은 `S = 1 / ((1-f) + f/r)`다. `f`는 해당 프로파일의 자기 시간 비중이고 `r`은 그 부분의 가속률이다. 소멸 상한은 `r → ∞`를 뜻한다. 실제 컴파일러가 이 비중을 전부 제거한다는 뜻은 아니다. mypyc 범위는 세 모듈의 자기 시간과 그 직접 C 호출 비용으로 계산했고, 가져다 쓰는 미컴파일 모듈의 시간은 포함하지 않았다.

| 표본·대상 | 비중 f | 해당 부분 2배일 때 | 해당 부분 5배일 때 | 해당 부분이 사라질 때 |
| --- | ---: | ---: | ---: | ---: |
| 상위 10개 / objects·content·paths | 77.40% | 1.63배 | 2.63배 | 4.42배 |
| 상위 10개 / 스캐너 | 38.19% | 1.24배 | 1.44배 | 1.62배 |
| 300개 / objects·content·paths | 80.94% | 1.68배 | 2.84배 | 5.25배 |
| 300개 / 스캐너 | 37.36% | 1.23배 | 1.43배 | 1.60배 |

300개에서 C 스캐너의 실측 1.65배는 프로파일 비중을 고정한 소멸 상한 약 1.60배보다 크다. 이 차이를 맞추려고 분류나 조건을 바꾸지 않았다. 프로파일 비중은 계측 오버헤드를 포함하며 벽시계 비용의 정확한 분해가 아니므로, 이론 표는 병목 범위를 이해하는 조건부 추론에만 사용하고 채택 판단에는 교대 측정의 실측값을 사용한다.

## 프로토타입 A: 기존 소스의 mypyc 컴파일

`objects.py`, `content.py`, `paths.py`를 사본에서 `mypycify`의 `opt_level="3"`, `--follow-imports=skip`으로 함께 컴파일했다. 다른 모듈은 해석형 그대로다. 세 모듈의 원본을 그대로 넣으면 타입 오류 20건으로 실패했다. 리스트·사전 타입, 가변 길이 run 튜플, 행렬 타입, 실행 중 추가하는 `form_loader`·`resources`·`properties` 선언을 보강했다. 선언 없는 함수의 안내 메시지만 남아도 이 도구 버전의 빌드가 종료돼 `annotation-unchecked` 안내만 끄고 진행했다. 타입 오류를 끄거나 기존 테스트의 단언을 바꾸지 않았다.

컴파일된 세 모듈의 `.so`가 실제 로드됐는지 모든 배치 결과에 기록했다. 사본의 변경량은 추가 36줄·삭제 19줄이다. 그중 타입 보강 외의 호환성 조치는 아래와 같다.

| 관찰 | 재현 근거 | 프로토타입 조치 |
| --- | --- | --- |
| `PDFName(str)`의 기본 타입 상속을 컴파일러가 거부한다. | `Inheriting from most builtin types is unimplemented`가 발생했다. | `native_class=False`로 Python 클래스 형태를 유지했다. |
| 데이터 클래스의 `object` 타입 필드에서 import가 실패한다. | `FontInfo.encoding_cmap` 선언에서 `KeyError: 'object'`가 발생했다. | 데이터 클래스는 Python 클래스로 유지하고 해당 필드 타입을 `Any`로 넓혔다. |
| 음수 시작 bytes 슬라이스가 Python 동작을 보존하지 못한다. | 기존 `test_lexer_differential_random_bytes_and_boundaries`에서 `SystemError: Negative size passed to PyBytes_FromStringAndSize`가 발생했다. | 음수 분기만 `operator.getitem(data, slice(...))`으로 Python 슬라이스 경로를 사용했다. |
| 빌드 도구가 없는 환경에서 import가 실패한다. | 같은 Python 3.12 비교 환경에서 `ModuleNotFoundError: mypy_extensions`가 발생했다. | 제품에는 넣지 않았다. 빌드 지시자 분리와 의존성 없는 로더는 제품 통합 전 해결해야 한다. |

최종 mypyc 사본과 결합 사본에서 기존 `tests/test_pdf_speed_differential.py`의 여섯 합성 테스트 함수를 그대로 실행해 모두 통과했다. 모듈 단위 컴파일은 가능하지만 무수정 컴파일은 아니고, 이 사본 자체가 배포 가능한 구현이라는 뜻도 아니다.

## 프로토타입 B: 내용 스트림 스캐너만 Cython으로 작성

92줄의 `cscan.pyx`를 직접 작성했다. 바이트 공백·주석·일반 토큰과 간접 참조의 예비 판별만 C 반복문으로 읽는다. 기존 `next() -> (종류, 값)`과 변경 가능한 `pos`를 유지해 해석기의 피연산자·연산자 처리를 그대로 연결했다. 모든 연산자 레코드를 미리 쌓지 않고 한 토큰씩 반환한다. 문자열·이름·배열·사전·손상 객체 처리는 기존 `PDFLexer`에 맡긴다. inline image를 건너뛴 `pos`도 다음 호출에서 반영한다. 이름과 경계 바이트는 기존 소스 및 ISO 32000-1 §7.2.2의 계약을 기준으로 사용했으며 외부 PDF 엔진 구현을 읽거나 옮기지 않았다.

사본의 연결 코드는 추가 4줄·삭제 1줄이고 기존 Python 스캐너도 사본에 남겼다. C 스캐너에서는 원본 스캐너와 무작위·경계 바이트 20,009개에서 값·위치·연산자 순서를 차등 비교했다. 닫히지 않은 문자열·배열, 중첩 한도, 주석을 낀 간접 참조, inline image도 포함했다. 8MiB 공백 뒤 숫자 처리의 5초 한도, 음수 위치 거부, EOF 밖 위치, `Py_ssize_t` 범위 초과 위치, 200MiB 초과 버퍼 거부를 확인했다. 대형 합성 버퍼는 메모리에서만 만들고 프로세스 종료 때 해제했다.

경계 검사는 직접 포인터를 읽기 전에 `i < n`, `second < n`, `second + 1 == n` 등을 확인하는 방식이다. 음수 위치는 포인터 접근 전에 거부하고 버퍼 참조는 호출 동안 보유한다. 별도 `malloc`이나 포인터 쓰기는 없으며 토큰·반환 객체의 할당은 CPython에 맡긴다. 입력 버퍼 상한은 200MiB이고 기존 객체 컬렉션 100,000개·중첩 깊이 64·피연산자 보유 64개·Form 확장 예산은 그대로다. 버퍼 한도 오류는 기존 PDF 리더의 페이지 단위 예외 처리에서 `doc.errors` 경고가 된다. 이 새 한도 밖 입력의 출력 동일성은 주장하지 않는다.

이 검사와 공개 문서 검증은 ASan·UBSan·장기 퍼징을 대체하지 않는다. 해당 검증, Cython 생성 코드 감사, 모든 지원 환경의 오류 복구 검증은 이번 조사에서 하지 않았으므로 메모리 안전 인증이나 제품 배포 완료를 주장하지 않는다.

## 결합 방식과 배포 영향

결합 사본은 mypyc 컴파일 전에 C 스캐너를 연결했다. 컴파일된 코드가 예전 native 스캐너를 직접 호출하는 상황을 피하기 위해 연결을 컴파일 이후 monkey patch로 하지 않았다. C 스캐너의 `data`·`pos`·`next` 타입을 알리는 작은 `.pyi`도 사본에만 만들었다. 세 Python 모듈의 변경량은 추가 40줄·삭제 20줄이고 별도로 C 스캐너 92줄과 타입 스텁·빌드 스크립트가 있다.

| 방식 | 운영체제·CPU·Python 휠 | 소스 설치 | 순수 Python 폴백 | abi3 | 보안·유지 비용 |
| --- | --- | --- | --- | --- | --- |
| 현재 순수 Python | 기존 범용 휠을 유지한다. | 컴파일러가 필요 없다. | 현재 구현 자체다. | 적용 대상이 없다. | 기존 Python 경로 한 개를 검증한다. |
| mypyc | 현재 산출물은 macOS arm64·CPython 3.12 전용이다. OS·CPU·Python별 빌드가 필요하다. | 컴파일을 선택하면 mypyc와 C 컴파일러가 필요하다. | 사본을 그대로 덮어쓰는 방식에는 자동 폴백이 없다. 별도 로더와 빌드 지시자 분리가 필요하다. | 이 산출물은 CPython 전용 ABI다. abi3를 입증하지 않았다. | 클래스·슬라이스·동적 속성 계약과 해석형·컴파일형 경로의 동일성을 계속 검사해야 한다. |
| C 스캐너 | 일반 빌드는 macOS arm64·CPython 3.12 전용이다. 제한 API 빌드라면 Python 버전 축을 줄일 수 있다. OS·CPU 축은 남는다. | `.pyx`에서 빌드하면 Cython과 컴파일러가 필요하다. 생성 C를 배포하는 설계라면 Cython 없이 C 컴파일러만 사용할 수 있지만 이번에 소스 배포를 만들지는 않았다. | 선택적 확장 import가 실패할 때 기존 스캐너로 돌아가는 로더가 필요하다. | `Py_LIMITED_API=0x03090000`, `py_limited_api=True`로 `cscan.abi3.so`를 실제 빌드했다. Python 3.9와 3.12에서 같은 20,009개 차등 검사가 통과했다. | 신뢰하지 않는 바이트를 C로 읽으므로 경계·예산·sanitizer·퍼징 검증을 추가해야 한다. 토큰 경로 둘을 계속 비교해야 한다. |
| 결합 | mypyc 모듈 때문에 전체 조합은 여전히 Python 버전별 빌드가 필요하다. | 두 빌드 도구와 컴파일러가 필요하다. | 클래스 정체성과 상호 import를 고려한 묶음 단위 폴백이 필요하다. | C 스캐너만 abi3여도 결합 전체는 abi3가 되지 않는다. | 가속기 조합과 폴백 조합까지 검증 행렬이 늘어난다. |

C 스캐너 abi3 빌드는 일반 CPython 3.12 빌드와 별개로 검증했다. 위 성능 비교표는 일반 빌드의 수치이며 abi3 빌드의 속도 보장은 아니다. Linux·Windows·다른 CPU와 Python 3.10·3.11·3.13은 미검증이고 실제 wheel 설치나 sdist 빌드도 하지 않았다. 설치된 도구 메타데이터의 라이선스는 mypy·mypy_extensions가 MIT, Cython이 Apache-2.0이다. 제품화 때 생성 런타임의 NOTICE 처리를 별도로 검토해야 한다. 이번에 런타임 의존성, `pyproject.toml`, 빌드·배포 구성은 변경하지 않았다.

같은 이름의 `.so`와 `.py`가 같이 있으면 확장 모듈 import가 실패했다는 이유만으로 Python 파일에 자동으로 돌아간다고 가정할 수 없다. 선택적 확장을 별도 이름으로 불러 실패를 처리하는 로더 설계와 두 경로의 모델 타입 호환 검증이 필요하다. 제품 폴백 로더는 이 조사에서 구현하지 않았다.

## HWP·Office의 작은 표본

각 형식은 제공된 표본 목록의 앞 50개를 사용했다. 무작위로 새 표본을 뽑은 실험이 아니므로 코퍼스 전체에 일반화하지 않는다. PDF 가속 모듈만 바꾼 음성 대조 측정에서는 HWP·HWPX·DOCX·PPTX·XLSX·XLS의 세 출력 해시가 각각 50/50건에서 세 회차 모두 같았다. 해당 형식이 PDF 스캐너를 실행하지 않으므로 그 가속 효과를 주장하지 않는다.

동일한 컴파일 방식의 이득도 확인하려고 별도 사본에서 `cfb.py`와 `hwp/records/para_text.py`를 mypyc로 컴파일했다. 문단 파서의 리스트 타입을 보강하고 CFB 클래스는 Python 클래스 형태를 유지했다. 제품 소스는 변경하지 않았다. 기존 CFB·제어 문자 합성 테스트 117개를 이 사본에서 통과시킨 뒤 순수 Python과 AB/BA/AB로 비교했다. 표는 세 회차 합계의 중앙값이며 모든 형식에서 세 회차의 Markdown·JSON·오류 해시가 같았다.

| 형식 | 순수 Python 50개 (초) | CFB·HWP 문단 컴파일 50개 (초) | 가속 | 출력 해시 |
| --- | ---: | ---: | ---: | --- |
| HWP | 1.4478 | 1.3484 | 1.074배 | 50/50 일치 |
| HWPX | 1.6336 | 1.6264 | 1.004배 | 50/50 일치 |
| DOCX | 0.2367 | 0.2379 | 0.995배 | 50/50 일치 |
| PPTX | 0.1554 | 0.1531 | 1.015배 | 50/50 일치 |
| XLSX | 1.2937 | 1.3187 | 0.981배 | 50/50 일치 |
| XLS | 6.1039 | 6.0601 | 1.007배 | 50/50 일치 |

이 범위에서 HWP는 약 7% 줄었지만 Office 형식의 차이는 작고 일관되지 않았다. HWPX·OOXML은 해당 두 모듈을 주로 사용하지 않아 이득의 근거가 없다. 대량 HWP 전용 경로의 추가 조사 여지는 있지만, 이 표본만으로 Office 전체 컴파일을 권하지 않는다. 다른 Office 파서의 주요 루프를 컴파일했을 때의 이득은 미검증이다.

## 권고와 남은 검증

PDF 대량 변환에는 작은 선택적 C 스캐너부터 제품화 후보로 검토할 수 있다. 실측은 현재 순수 Python 대비 300개 1.65배, 느린 30개 1.56배였고 클래스·레이아웃 출력 경로를 넓게 바꾸지 않았다. 제한 API 빌드도 가능했다. 제품화 전에는 의존성 없는 로더, 순수 Python 폴백, 입력 한도 경고, 지원 환경별 wheel 설치, sanitizer·퍼징을 확인해야 한다. 기본 설치 경로를 바꾸는 일은 이번 조사에 포함하지 않는다.

추가 비용을 감수하면 mypyc와 C 스캐너의 결합은 약 2배 후보가 된다. 실제 합계는 300개 2.28배, 느린 30개 2.05배였다. mypyc 단독은 각각 1.31배·1.23배이고 현재 사본은 빌드 지시자 패키지를 런타임에 import하므로 그대로 채택하면 새 런타임 의존성 금지 조건을 어긴다. 그 import를 분리한 새 사본과 폴백을 검증하기 전에는 제품에 넣지 않는 것이 타당하다.

결합해도 PyMuPDF 대비 공통 성공 문서의 파싱+Markdown 시간은 300개에서 3.88배, 상위 30개에서 5.04배다. 출력 계약이 다른 비교 도구와 동등한 속도에 도달했다고 주장하지 않는다. 완벽한 컴파일을 가정한 암달 표나 한 호스트의 결과를 모든 문서의 가속률로 보장하지 않는다.

PDF가 드물거나 이미지·OCR·외부 입출력이 전체 시간을 지배하는 작업, 운영체제별 wheel 유지 비용을 감당하기 어려운 배포에서는 순수 Python을 유지하는 판단도 가능하다. 이번 표는 import·첫 문서 비용과 OCR 작업을 측정하지 않아 그 작업의 이득은 미검증이다. HWP·Office 전체를 함께 컴파일하는 범위 확장은 이번 실측으로 정당화되지 않는다.

## 재현과 산출물

측정 스크립트는 새 런타임 의존성을 import하지 않으며 `--backend pymupdf`를 명시할 때만 별도 도구 환경의 PyMuPDF를 불러온다. `--accelerator-root`는 검토할 사본을 명시하는 옵션이고 원본 패키지를 변경하지 않는다. 경로 JSON 배열은 명령 인자로 받는다.

```bash
python -m scripts.probe_speed_pdf --batch-list files-pdf.json --output .codex-work/pure.json
python -m scripts.probe_speed_pdf --batch-list files-pdf.json --accelerator-root .codex-work/proto/mypyc --output .codex-work/mypyc.json
python -m scripts.probe_speed_pdf --batch-list files-pdf.json --accelerator-root .codex-work/proto/cscanner --output .codex-work/cscanner.json
python -m scripts.probe_speed_pdf --batch-list files-pdf.json --accelerator-root .codex-work/proto/combined --output .codex-work/combined.json
python -m scripts.probe_speed_pdf --batch-list files-pdf.json --backend pymupdf --output .codex-work/pymupdf.json
python -m scripts.probe_speed_pdf --batch-list files-pdf.json --batch-profile --output .codex-work/profile.json
```

원시 결과는 `.codex-work/proto/`의 `pdf300-<방식>-<회차>.json`, `top30-<방식>-<회차>.json`, `profile-top10.json`, `profile-pdf300.json`, `summary.json`, `summary-extra.json`에 있다. 프로토타입은 `mypyc/`, `cscanner/`, `combined/`, `abi3/`, `office-mypyc/`에 있고 소스·타입 스텁·`setup.py`·바이너리와 원본 대비 diff를 남겼다. 각각의 폴더에서 설치된 가속 도구 Python으로 `setup.py build_ext --inplace`를 실행해 빌드했다. 해당 사본들은 git 제외이므로 새 checkout에는 따라오지 않는다. 제품 빌드 설정이나 설치 절차를 만들었다는 뜻은 아니다.

일반 가속 빌드의 소스·바이너리 SHA-256은 `.codex-work/proto/manifest.json`에 기록했다. C 스캐너 원문 SHA-256은 `64258b5c689f5354fef9653aa7c9e807c981443927eb40fc001a4af0b2d28359`다. 빌드된 `.so` 파일 이름도 각 배치의 `loaded_modules`에 기록해 가속기 대신 순수 Python을 측정하는 일을 확인했다. 출력 본문, PDF 원본, 생성 C 파일과 바이너리는 커밋하지 않는다.

abi3 사본은 Python 3.12에서 PDF 300개와 상위 30개를 각각 한 번 변환해 세 해시가 모두 일치했다. 이 확인은 출력 보존 검사이고 그때의 시간은 교대 성능 비교표에 넣지 않았다. 원시 결과는 `abi3-pdf300.json`, `abi3-top30.json`이다.

원본 런타임의 전체 테스트는 지정된 Python 3.9 명령으로 5,450 passed, 36 skipped, 14 xfailed였고 `ruff check dochan scripts tests`도 통과했다. 프로파일 자기 시간 보존과 배치 실패 기록·SIGALRM 복구도 합성 검사로 확인했다. 기존 테스트의 단언과 원본 런타임·패키징·배포 파일은 변경하지 않았다.
