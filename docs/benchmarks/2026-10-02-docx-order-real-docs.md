# DOCX 읽기 순서 실물 검증

2026년 10월 2일, 브랜치 `illuwa/w-docx-order`의 기준 커밋 `16f715ce456c8881ff81a43fb92aed28a52a359d`와 변경 후 리더를 비교했다. README는 수정하지 않았다. DOCX 읽기 순서는 **⬜ 유지를 제안한다.** Transitional OOXML 대상의 검증은 통과했으나 확장 집합의 Strict OOXML 두 문서는 본문을 읽지 못했다.

## 판정과 분모

LibreOffice `sw/qa/extras/ooxmlexport/data`의 DOCX 1,366개를 읽기 전용으로 스캔했다. XML을 읽은 파일은 1,359개이며 손상·비 ZIP 등으로 읽지 못한 파일은 7개다. 텍스트박스, 떠 있는 도형, 콘텐츠 컨트롤, 그룹 도형 중 하나가 저장된 **466개 전부**를 비교했다. 파일을 결과에 따라 선택하거나 성공 사례만 남기지 않았다. 기존 후보 465개에 그룹 도형만 있는 `inline-groupshape.docx`가 추가됐다.

## 정답 토큰열의 계약

본문의 XML 순서가 논리 순서다. 도형의 페이지 좌표나 z-order로 재정렬하지 않는다. 텍스트박스·그룹 도형은 부모 앵커에서 한 번 펼치며 콘텐츠 컨트롤과 변경 추적의 삽입·이동 목적지를 투명 래퍼로 취급한다. 삭제·이동 원본과 비활성 AlternateContent 갈래는 제외한다. 현재 리더의 기존 계약대로 첫 Choice를 선택하며 Choice가 없으면 Fallback을 택한다. 모든 확장 네임스페이스의 Requires 협상 지원을 주장하지 않는다.

기존 `xml_body_text`와 `align_tokens`는 유지했다. 새 `logical_body_text`는 리더를 호출하지 않고 원시 XML·관계·번호 정의·주석 파트에서 이미지 Markdown 참조, 링크 주소, 목록 번호, 도형 대체 설명, 각주 번호, 주석 표지를 기대 위치에 구성한다. 출력에서 정규식으로 표지를 삭제하지 않는다. 문자로 쓰인 `![image](...)`, `[comment 1]`, `<#anchor>`도 보존하여 중복·누락 검사에서 빠지지 않는다. 외부 URL의 퍼센트 인코딩은 원형을 유지한다. 원시 수식의 순서는 독립적으로 정하며 LaTeX 표기 변환만 기존 공용 OMML 변환기를 재사용한다. 따라서 이는 수식 변환기의 수학적 정확성에 대한 독립 인증은 아니다.

차트는 본문의 관계 앵커에서 원시 캐시의 계열명·범주·값·축·제목을 기대열로 만든다. 산포 차트는 X/Y 캐시를 별도로 읽는다. 검증기가 지원하지 않는 차트 형식은 ValueError로 미검증 처리하며 성공으로 제외하지 않는다. 이번 여섯 차트 파일의 캐시와 앵커는 모두 비교 가능했다. 이미지 참조의 위치·개수는 토큰열에 남기며 OCR 텍스트·이미지 자체의 시각적 의미는 검증하지 않는다.

표의 앞뒤에는 양쪽 모두 `⟦TABLE⟧`와 `⟦/TABLE⟧`를 추가해 빈 표와 중첩 표도 비교한다. 셀은 행 우선 순서이며 병합으로 가려진 셀은 제외한다. 캡션은 기존 모델의 TOP/LEFT 또는 BOTTOM/RIGHT 위치에서 읽는다. 문단·탭·줄바꿈의 공백 차이만 정규화하고 `\w+|[^\w\s]` 토큰열 전체를 SequenceMatcher(autojunk=False)로 비교한다. 삽입·삭제·대체를 모두 세며 부분 순서나 다중집합 일치를 성공으로 쓰지 않는다. JSON의 최상위 `reading_order[*].exact`는 표 경계를 포함한 결과이고, 종전 비교는 `raw_wt`에 보관한다.

머리글→본문→꼬리글→각주/미주 정의의 배치는 별도 `story_evidence`에서 확인한다. 각주·미주는 본문에서 처음 참조한 순서로 번호를 부여하고 정의를 뒤에 둔다. 기존 DOCX `test_reads_docx_headers_and_footers_from_section_relationships`, `test_reads_docx_footnotes_and_endnotes`, DOC `test_doc_stories.py`, PPTX `test_pptx_remaining.py`의 수식 앵커 계약을 따랐다. 페이지별 시각적 재배치나 머리글의 페이지 반복은 논리 순서 검증에 포함하지 않는다.

## 남은 불일치와 한계

`strict.docx`와 `tdf116410.docx`는 `http://purl.oclc.org/ooxml/wordprocessingml/main`을 사용한다. 현재 리더는 Transitional 네임스페이스에서 body를 찾으므로 `ERR: DOCX body not found`를 남긴다. 이는 두 파일의 순서를 증명하지 못한 실제 리더 한계다. 검증기는 이를 미검증으로 표시하고 466개 분모에 그대로 남겼다. 두 빈 문자열을 비교하던 종전 방식의 거짓 성공도 단위 테스트로 차단했다. Strict 파트·관계·수식 네임스페이스 전반의 지원은 이 변경에 끼워 넣지 않았으며 후속 과제로 남긴다.

정상 Transitional 464개가 통과했다는 결과를 모든 DOCX 변종의 지원으로 확장하지 않는다. XML을 읽지 못한 7개도 원래 스캔 분모와 함께 공개했으며 성공률에서 조용히 숨기지 않았다. 코퍼스 파일은 복사·수정하지 않았고 내부 문서의 파일명이나 내용은 사용하지 않았다. README의 읽기 순서는 Strict 실패가 해소되거나 오케스트레이터가 지원 범위를 명시하기 전까지 ⬜로 유지한다.
