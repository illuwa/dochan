## HWP 배포용 문서

변경 전에 `scripts/probe_hwp_distribution.py` 결과를 확보했다. 새 구현으로 동일한
프로브를 실행한 JSON 전체가 변경 전과 동일했다. 공개 HWP 5,363개를 스캔했고,
그중 배포용 27파일·65섹션에서 오류 없이 본문을 얻었다. 중복 파일을 SHA-256으로
제외하면 배포용 파일은 20개다. 정렬된 CRC32·ISIZE trailer 64개와 연속 8바이트 trailer
1개가 모두 일치했다. 이 프로브는 키 스크램블 함수와 AES 함수를 생산 코드와 공유하므로
암호 구현 전체가 독립적인 정답지는 아니다. 복호화 뒤 CRC·길이·레코드·본문 비교는
원시 바이트에서 수행하며, 한컴 명세와 기존 합성 테스트를 함께 근거로 삼았다.

직접 일치했고, 링크 주석을 제외하면 71,435개 모두 일치했다. 3개 차이는 변경 전에도

## 명세의 공백과 선택 근거

배포용 revision 1.2의 2.2절에는 MS Visual C의 `rand()`를 사용한다고만 적혀 있다.
LCG 상수 214013·2531011, 32비트 상태와 반환 비트 규칙은 명세에서 찾지 못했다.
알려진 MS Visual C 호환 규칙을 새 수식으로 작성하고 공개 실물의 복호화 결과로
검증했다. 따라서 “명세만으로 모든 수치가 도출된다”는 주장은 하지 않는다.

CRC·길이 trailer의 세부 배치도 두 한컴 문서에서 찾지 못했다. 공개 실물 65섹션에서
검증한 두 배치와 기존 합성 테스트의 trailer 없는 영 패딩만 허용한다. 정상 압축 EOF
이후 trailer를 제거하여 기존 섹션 파서가 압축 해제를 수행하는 반환 계약을 유지했다.
출력 크기는 기존 200 MiB 제한을 사용하며 입력은 기존 OLE 스트림 상한을 적용한다.
상한 초과나 손상은 ValueError로 반환되어 기존 reader의 섹션별 doc.errors에 기록된다.

2.3절의 XOR 대상 중 앞 네 바이트를 내부 함수에서 보존하는 것은 기존 프로브의
호출 계약이다. seed로부터 키 offset을 먼저 계산하고 4 이후의 바이트에 동일한 난수
배열을 XOR하므로 실제 키 결과는 명세와 같다. 확장 크기 레코드 헤더는 HWP5 4.1절의
공통 규칙을 적용했다. 새 출력 모델이나 의존성을 만들지 않았다.

한컴 두 명세는 dochan으로 각각 3,966자와 59,413자를 추출했으며 파서 오류는 없었다.
배포용 명세 파일 SHA-256은
`0d32f102ec60f24dd0479d229ab5bede21975ec81f8505c7ebfcc0da2f225e61`이고,
HWP5 명세 파일 SHA-256은
`f21edf2138e134702366f2fb6a2ab082b05c6dcb42216ec4fa2575ed292efd1d`이다.
추출 텍스트는 검증 작업 디렉터리에만 두며 배포물로 넣지 않는다.

## 내부 문서 회귀와 단위 테스트

내부 실물 76쌍을 HWPX 정답지로 변경 전후 비교했다. 모든 쌍별 수치의 직렬화 해시가
같았고 오류가 발생한 쌍은 0개다. 평균 텍스트 비율은 0.9997, 표 구조 일치율은
0.9987, 평균 셀 일치율은 0.9991, 중첩 구조와 비교 가능한 서식 일치율은 각각 1.0이다.
이 수치를 완전 일치 100%로 바꾸어 보고하지 않는다. 내부 파일명과 내용은 저장하지 않았다.

변경 전 신규 테스트는 13개 실패·12개 통과를 확인했다. 실패는 새 원본 입력 인자,
입력 크기 및 seed 블록 검증, 확장 레코드 헤더, 빈 AES 암호문 경계였다. 재구현 뒤
기존 배포용 테스트를 포함한 관련 테스트는 61개가 모두 통과했다. 기존 테스트의
단언은 변경하지 않았다. 전체 결과는 3,046개 통과, 24개 건너뜀, 14개 예상 실패다.

