# 공통 출력 계층 속도·메모리 — JSON 직렬화, 행 단위 직렬화, import 시간

2026-10-06. 형식별 리더가 아니라 9개 형식이 함께 쓰는 곳(출력 계층·공용 모델 도우미·패키지 import)을 고쳤다.
출력은 한 글자도 바뀌지 않았고 `to_dict()`·JSON 스키마·API·CLI 도 그대로다. 요소 지원을 더한 작업이 아니므로
README `Supported Elements` 표는 바꾸지 않는다.

## 무엇이 느렸나

형식마다 실물 40개를 뽑아 프로파일러를 켠 채 파싱·Markdown·JSON·일반 텍스트 단계를 따로 쟀더니(Python 3.9), JSON 출력이
파싱만큼 또는 그보다 훨씬 오래 걸렸다: XLS 는 파싱 4.8초에 JSON 82.3초, XLSX 4.8초에 25.8초, HWP 0.8초에 0.8초, DOC 0.3초에 0.4초.
프로파일의 1·2위는 형식과 무관하게 표준 라이브러리 `json/encoder.py` 의 `_iterencode_dict`·`_iterencode_list` 였다.
CPython 3.12 이하는 `indent` 를 주면 C 인코더를 쓰지 않고, 토큰 하나가 중첩 깊이만큼의 제너레이터를 거쳐 올라오는
순수 Python 경로로 떨어진다. `to_json()` 의 기본값이 `indent=2` 라서 모든 호출이 이 경로를 탔다.

같은 프로파일에서 두 가지가 더 보였다. 공용 평탄화 도우미 `flatten_block_texts` 가 `hasattr(block, 'text')` 로
프로퍼티를 평가해 문단 하나의 글자를 세 번씩 다시 만들었고, `dochan.utils.aes` 가 S-box 의 곱셈 역원을 255×255
전수 탐색으로 구해 `import dochan` 마다 약 27ms(전체의 28%)를 썼다.

## 바꾼 것

1. **들여쓰기 JSON 직렬화기** (`dochan/output/json_indent.py`). `json.dumps(obj, ensure_ascii=False, indent=N)` 과 결과가
   바이트 단위로 같은 재귀 함수다. 표준 라이브러리와 같은 `isinstance` 순서를 지키므로 `str`·`int`·`float` 하위 클래스,
   `tuple`, 문자열이 아닌 키도 같게 나온다. 다루지 않는 값·순환 참조·잘못된 `indent` 는 표준 라이브러리에 그대로 넘겨
   같은 결과나 예외를 낸다. C 인코더가 들여쓰기를 직접 내는 인터프리터(실측: 3.13.16·3.14.8)는 표준 라이브러리가 더
   빠르므로 위임한다(가져올 때 동작으로 판별).
2. **행 단위 직렬화**. `to_json()` 이 문서 전체의 dict 트리를 만들지 않고 섹션·요소·표의 행을 하나씩 만들어 쓰고 버린다.
   `to_dict()` 와 같은 변환 함수를 쓰고 목록을 만드는 방법만 다르다(`list` 또는 지연 목록 `Stream`). 쌓인 문자열 조각이
   4,096개를 넘으면 꼬리를 한 문자열로 합친다. 지연 경로가 실패하면 전체 dict 경로로 물러난다.
3. **공용 도우미의 중복 계산 제거**. `flatten_block_texts` 는 문단이면 속성 판별 없이 글자를 한 번만 만든다.
   `Paragraph.text` 는 리스트 컴프리헨션으로, 출처 정보 변환은 정확한 `Provenance` 타입이면 필드를 직접 읽는다.
4. **import 시간**. S-box 역원을 생성원 3 의 거듭제곱 표로 구하고(x = 3^k 이면 x^-1 = 3^(255-k)), 32비트 T-테이블은
   처음 암·복호화할 때 만든다. 결과 표는 전수 탐색·FIPS-197 Figure 7 값과 같다.

## 속도

Apple M5 Pro, Xcode Python 3.9.6, 작업자 8개. 변경 전 스냅숏(`116e126`)과 변경 후(`83fb2f4`)를 전·후·후·전·전·후 순서로
여섯 번, 매번 15,216건 전부를 변환했다. 값은 문서별 단계 시간의 합계이고 세 번의 중앙값이다. 무거운 작업을 함께 돌리지
않았지만(측정 중 import 시간 확인 같은 짧은 명령은 실행했다) 열 상태와 파일 캐시는 통제하지 않았다. 파싱 코드는 바꾸지 않았으므로 파싱 열의 차이는 측정 변동이다.

### 큰 표의 시간과 메모리

20열 합성 XLSX(숫자와 공유 문자열이 섞임)를 새 프로세스에서 한 번씩 변환했다. 최대 RSS 는 파싱·Markdown·JSON·일반
텍스트를 모두 낸 뒤의 값이다.

| 셀 수 | JSON 시간 전 → 후 (초) | 일반 텍스트 전 → 후 (초) | 최대 RSS 전 → 후 (MB) |
| ---: | ---: | ---: | ---: |
| 100,000 | 3.97 → 1.21 | 0.08 → 0.05 | 1,480 → 933 |
| 198,000 | 7.93 → 2.51 | 0.18 → 0.10 | 2,892 → 1,817 |

198,000셀의 JSON 은 3억 5,224만 글자다. 한글이 들어 있어 Python 이 글자당 2바이트로 저장하므로 결과 문자열 하나가
704MB 이고, 합치기 직전의 조각들도 그만큼을 쓴다. 남은 1.8GB 의 대부분이 이 둘이다. `to_json()` 이 문자열 하나를
돌려주는 한 줄일 수 없는 부분이고, 파일로 흘려 쓰는 API 가 있어야 없어진다(아래 "남은 일").

### import 시간

`python -X importtime -c "import dochan"` 을 변경 전·후 교대로 다섯 번: 97.1 / 97.3 / 96.3 / 91.6 / 92.9ms →
60.5 / 63.8 / 64.7 / 63.8 / 63.3ms(중앙값 96.3 → 63.8ms). `dochan.utils.aes` 자체는 27.5ms → 0.26ms 다. 모든 CLI 호출과 배치 작업자 프로세스 시작이 형식과 무관하게 이만큼 빨라진다.

## 시도했지만 넣지 않은 것

- **평평한 dict 를 C 인코더에 넘기는 혼합형**. 값이 모두 스칼라인 dict(런·출처 정보)를 깊이별 구분자를 가진 C 인코더로
  한 번에 적는 방식은 호출·평평함 검사 비용이 이득을 상쇄해 순수 재귀 함수와 같았다(2.9배 대 2.9배). 비공개 API
  (`json.encoder.c_make_encoder`) 의존만 늘어 버렸다. 정확한 타입 분기를 인라인한 쪽이 더 컸다(2.9 → 3.4배).
- **공용 모델의 슬롯 저장**. `TextRun`·`Paragraph`·`Cell`·`Provenance` 를 `__slots__`(임시 속성용 `__dict__` 슬롯 유지)로
  바꾸면 파싱 뒤 살아 있는 모델 메모리가 100,000셀 XLSX 에서 105.4 → 71.8MB(-32%), 공개 XLS 1개에서 11.8 → 8.6MB,
  공개 HWP 1개에서 41.2 → 39.1MB 였고 파싱 시간은 약 5% 줄었다. 그러나 DOCX 리더가 캡션 결합 뒤 임시 XML 참조를 지울 때
  `value.__dict__` 로 모델 그래프를 훑는다(`_release_source_elements`). 슬롯으로 옮긴 필드는 그 사전에 없어 표 셀 안
  문단의 참조가 남았고(`test_docx_completed_model_does_not_retain_xml_elements` 실패), 고치려고 `__dict__` 를 건드리면
  모든 객체에 빈 사전이 생겨 이득이 사라진다. 전체 테스트를 돌리며 센 결과 리더들이 모델 객체에 붙이는 필드 밖 속성은
  클래스·속성 조합으로 17가지였다(`_source_element`·`_caption_kind`·`_pdf_heading`·`_textbox_start` 등). 임시 참조를 객체 그래프 순회 없이 지우도록 DOCX
  리더를 먼저 고친 뒤에 다시 본다.

## 남은 일

- JSON 을 파일로 흘려 쓰는 API(`to_json()` 의 결과 문자열과 합치기 전 조각이 최대 메모리의 대부분). CLI `convert -f json -o`
  와 배치가 쓰면 큰 시트의 최대 메모리가 모델 크기 근처로 내려간다.
- 3.13 이상에서는 표준 라이브러리에 위임하므로 행 단위 직렬화의 메모리 이득이 없다(전체 dict 트리를 만든다).
- import 의 나머지 약 64ms 는 여러 모듈에 0.6~2.3ms 씩 흩어져 있다. `ssl`·`email` 을 끌고 오는 표준 라이브러리 import 를
  늦추면 수 ms 가 더 줄 수 있다.
