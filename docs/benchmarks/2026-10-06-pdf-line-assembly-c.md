# PDF 줄 조립의 선택적 C 가속

2026-10-06. `dochan/pdf/content.py`의 기존 줄 조립 계약을 직접 작성한 `_clines.c`로 가속했다.
행 묶기·안정 정렬은 C, 표준 float/str/bool 조각만 있는 행은 `_Line.__new__`와 속성 대입으로 만든다.
링크·각주·주석·int 수치가 섞인 행은 정렬 뒤 Python `_Line(row)`에 맡긴다. 비유한 수치·콜백이 가능한
사용자 속성 등 확신할 수 없는 입력은 호출 전체를 Python으로 처리한다. 원래 클래스·Python 본문은 그대로다.

`DOCHAN_BUILD_ACCEL=1`일 때만 optional CPython 3.9 제한 API 확장을 빌드한다.
`DOCHAN_DISABLE_ACCEL=1`, 확장 없음·ImportError일 때 원래 Python을 쓰며 그 외 오류는 전파한다.
일반 wheel은 `py3-none-any`, 선택적 빌드는 `cp39-abi3`임을 확인했고, build-system·의존성은 바꾸지 않았다.

## 출력 동일성

공개 pdf.js 디렉터리와 정책브리핑 press-pairs 디렉터리에서 각각 이름순 앞 200개, 총 400개 PDF를 읽기만 했다.
pdf.js는 `160F-2019.pdf`부터 `bug1538111.pdf`, 보도자료는 `156783497.pdf`부터 `156783900.pdf` 범위다.
정답 근거는 같은 입력의 원래 Python 구현이다. 추출 정확도의 독립 정답지를 새로 검증한 결과는 아니다.

| 검사 | 실제 결과/판정 |
| --- | --- |
| 실물 `_assemble_lines` 입력 23,467회, 1,249,955조각·95,171행 | 모든 줄/세그먼트 필드·run의 타입과 실수 IEEE 비트 일치, 불일치 0 |
| 400개 Markdown·JSON·errors 각각의 SHA-256 | 줄 가속 교대 6회와 전체 비활성화에서 모두 일치 |
| 실제 Python 생성자 호출 | 403행(0.423448%), 예상 위임 조건과 일치 |
| C 직접 생성 | 94,768행, 전체 호출 폴백 0회 |
| 단위·회귀, 가속 켬/끔 | 각각 6,019 passed · 36 skipped · 14 xfailed |
| 시드 고정 무작위 조각 목록 | 20,000개, 타입·IEEE 비트 차등 통과 |

위임 사유는 중복 집계로 int `dir_x` 375행, int `dir_y` 375행(같은 행), 링크 30행, 각주 6행, 주석 4행이다.
pdf.js 110개·보도자료 5개에는 원래 errors 항목이 있었고 총 131개 항목을 그대로 보존했다.
완전한 선정 목록·원본/출력/구현 해시·시간 원값은 로컬 작업 기록 `.codex-work/pdf-clines-probe.json`에 남겼다.

## 속도

macOS 26.6.2 arm64, Xcode Python 3.9.6. 전체 테스트와 sanitizer 작업을 마친 뒤
C→Python을 3회 교대로 실행했다. **기존 C 스캐너를 양쪽에서 고정하고 줄 가속만** 비교했다.
파싱 합계에는 출력 직렬화/해시 시간을 포함하지 않는다. 줄 재생은 실제 입력의 호출 당시 상태를 다시 처리하며 검증/복사 비용을 제외한다.

| 측정 (초) | C 1/2/3회 | Python 1/2/3회 | 중앙값 Python÷C |
| --- | --- | --- | ---: |
| 전체 파싱 | 29.139107 / 29.727973 / 28.373500 | 32.841258 / 31.015672 / 30.933044 | 1.064400배 |
| 줄 조립 재생 | 2.322159 / 1.681125 / 1.778564 | 3.947963 / 4.584482 / 3.994596 | 2.245967배 |

두 중앙값은 각각 31.015672→29.139107초, 3.994596→1.778564초다.
다른 문서·인터프리터에서 같은 비율을 보장하지 않는다.

별도 새 프로세스에서 `DOCHAN_DISABLE_ACCEL` 없음/`1`로 두 가속을 모두 교대 3회 켜고 껐다.
ON 파싱 합계는 29.632320 / 28.702604 / 28.187685초, OFF는 45.477959 / 46.014539 / 46.179939초다.
중앙값 28.702604/46.014539초(1.603149배)는 **기존 스캐너와 줄 가속을 합친 효과**다.
이 추가 6회의 400개 문서 출력 해시도 전부 일치했고 원본 PDF와 구현 해시를 사후 확인했다.
이 결과는 `.codex-work/pdf-clines-env-timings.json`에 기록했다.

## 메모리와 확인 범위

- 원본 목록 저장 공간 대신 참조 스냅샷을 유지한다. 버퍼 크기·정렬/인근 창의 색인을 검사하고 실패 시 참조와 버퍼를 정리한다.
- 실제 수치 코어를 직접 포함한 `tests/pdf_clines_sanitize.c`의 200,000개 사례: ASan·UBSan 진단 0.
- 별도 sanitizer 확장 전체, Homebrew Python 3.11 framework 실제 실행파일: 96개 테스트 통과, 진단 0.
- Xcode Python 3.9의 선로드는 OS 정책으로 막혔다. macOS LeakSanitizer도 지원되지 않아 네이티브 누수 검사는 미검증이다.
  참조 수·GC·예외 정리는 Python 테스트로 별도 확인했다.
- 같은 abi3 파일을 Python 3.9/3.11에서 로드했다. Linux·Windows·다른 CPU 및 나머지 Python 버전은 실행 미검증이다.

재현:

```bash
DOCHAN_BUILD_ACCEL=1 /opt/homebrew/bin/python3.11 setup.py build_ext --inplace
/usr/bin/python3 -m scripts.probe_pdf_clines --count 200 --output .codex-work/pdf-clines-probe.json
```

## 후속 수정 (같은 날)

- **3.9 제한 API**: `PyMem_Calloc` 은 Python 3.9 헤더에서 제한 API 에 선언되지 않는다. 3.11 헤더로만 빌드해 확인했기 때문에 드러나지 않았고,
  3.9 로 빌드하면 컴파일이 실패해 optional 확장이 조용히 빠졌다. `PyMem_Malloc` + `memset` 으로 바꿨다. 지금은 Xcode Python 3.9 로 빌드한다.
- **호출마다 만들던 문자열**: 조각마다 15번쯤 부르던 `PyObject_GetAttrString` 과 줄·세그먼트마다의 `PyDict_SetItemString`·`__new__`·`__dict__` 조회가
  매번 C 문자열로 Python 문자열을 만들고 있었다. 모듈 초기화 때 한 번 만들어 쓰도록 바꿨다. 같은 400개(조각 125만 개)의 줄 조립 재생이
  2.44 → 0.68초(중앙값), 공개 300개 파싱 합계가 19.10 → 17.21초가 됐고, 실물 조각 차등·400개 출력 해시는 그대로 불일치 0 이다.
  이 수정 뒤의 전수 대조·퍼징·ASan 결과는 `2026-10-06-pdf-content-interpreter-c.md` 에 있다.
